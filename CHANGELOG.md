# Changelog

Every release of `papers-experiments-core`. Versions follow semantic versioning with tags `vMAJOR.MINOR.PATCH`; while the version is 0.x, a minor release may break interfaces, and its entry says which.

## 0.1.0 (unreleased)

The first release: what a study needs to run end to end on the core (agent loop, model backends, tools, prompts, records and replay, the campaign kernel, the statistics kernel, provenance and replication packages), with the Onedata platform layer: configuration, token planes, tool-server launch, health, the sandbox and its data paths, the data gate, provisioning and placement, platform probes, leased platform users and day-0 checks. A study depends on it by tag and copies nothing; [`docs/study-guide.md`](docs/study-guide.md) shows how. What the release guarantees is the list of regressions at the end of this entry: each has a test on this tree, named beside it, whose docstring starts with the ID. An ID of [`docs/regressions.md`](docs/regressions.md) that is not in the list is not guaranteed yet.

**The live contract tests have run against one throwaway deployment, and only the platform layer's REST paths have been exercised on it.** The platform layer is tested against fakes of the Onedata API and of the MCP server, and the contract tests in `tests/live/` skip unless `EXPCORE_LIVE_PLATFORM` names a deployment. They have run against the Compose federation of `deploy/compose-federation` (Onedata 25.0), whose dated day-0 reports and facts files are beside it. On that release they pass, both day-0 checks that change state included: the mutation gate finds a file's space, the pre-campaign content check measures, and provisioning creates, places, reads back, evicts and tears down. The sandbox and tool-server tests have not run against a live deployment, and a probe of the mount data path could not make its mount there.

### Added

- `expcore.campaign.shard` (#154): the interface for running one campaign as N shards on different hosts. The partition by pair, the shard spec and its operator-chosen label, the shares of caps and budget, the environment identity's form, and the names of what a shard records and a merge writes. Running, merging and reporting shards build on it.

The interfaces a study implements are in [`docs/interfaces.md`](docs/interfaces.md).

- Replication packages: `python -m expcore package STUDY --out DIR` builds what the study's `package.toml` lists and nothing else, with a SHA-256 manifest, a study-token check over every path and content, whole-word anonymisation lists for double-blind submissions, and a deterministic archive. The package's own `make check` (`python -m expcore package-check`) verifies every file and derives the tables and the report anew from the records, byte for byte; the build runs it before it writes anything. A package vendors one wheel per distribution of the environment its replay check ran under, and its `make check` installs them into a fresh environment with no index and no network; `PACKAGE.json` names that environment, and where each distribution came from. The study-token list applies to a vendored wheel by provenance: one whose SHA-256 the study's `uv.lock` records for that name and version from the pypi.org registry is a public release and skips that list alone, and `PACKAGE.json` lists it with the lock's hash; the core's wheel and anything installed from a URL, a repository or a directory never do. `--anonymise` also gives the package a code identity by tree hash alone: no commit id and no source URL of the study or the core, anywhere in it. Files no commit holds are warned about and listed, and refused in an anonymised build unless `--allow-uncommitted`. No message of the build, findings, warnings, hints and refusals alike, shows a path, a name or a value that holds a private name or a term: every check names such a path the same way, by the start of its SHA-256, a finding is reported once per occurrence at the file's line, and `--show-private-paths` prints the paths behind the hidden names for the author's own terminal. Any exception the build meets refuses it through the same redaction, `package-check` shows its problems through the core's public list, and no command of the core or of its provenance tools repeats an argument it does not take or prints an exception unredacted.

It is in the campaign fingerprint, so a resume under another one is refused, and the replay check and the analysis are bound to it.

- The platform probes record every transfer of the space that started in the run's window, whoever started it: the harness, the agent through the tool plane, or a QoS requirement. Every tracked provider's listing is read until two observations in a row agree, on a window moved onto the providers' clocks by their `Date` headers. Verification stays on by default. `ca_file` names a CA bundle the federation's certificate chains to; every client trusts the bytes whose SHA-256 was taken at load, never the configured file, so a bundle swapped afterwards is not trusted. `insecure_tls = true` turns verification off, for disposable test federations only, and every health reading warns while it is on. Each run's sandbox metadata records the mode, with the bundle's SHA-256 under `ca_file`, and a plugin puts it in the campaign fingerprint through `StudyPlugin.platform` (`PlatformConfig.fingerprint()`), so a resume under another mode or bundle is refused. - A REST data path can serve complete listings. `[sandbox.data_paths]` takes a table for a level, `level = { kind = "rest", listing = "complete" }`, and that level's data gate answers every listing with all of the directory's entries, in the server's order, as one last page; it follows the pages upstream itself, so a client that reads one page (the official client's `ls`) sees the whole directory. It fails closed: a page that neither ends nor continues the listing, gives a key twice, or gives a token or an entry the listing gave before, or a page after the first that is not a 200, is the platform's 502; a listing whose entries and tokens pass 64 MiB, or that passes 10,000 pages, is refused for the gate's integrity (`listing_too_large`), so its run is set aside; a listing that names where it starts is the agent's 400. A study selects the mode per condition through the level, and the run's metadata (`listing`) and `PlatformConfig.fingerprint()` record it. The earlier study's whole-file mode is not carried over.
- The bytes each run's agent read through its data path. The platform's second instrument, `ServedBytes` (namespace `served_bytes`), records the count the sandbox's collection takes once from the log of the gate it stopped: the body bytes of the platform's answers the gate served the agent, as file content, listings as served and other answers, with the gate's own answers apart. The same count comes per file and per directory, so a study can check its agent's claimed reads file by file: `files` has a row for each file whose content was served, keyed by the file id the request's path names, with that path as the gate logged it, the number of answers, the unique byte ranges served (merged, starting where the platform's answer says) with the bytes in them, and the body bytes; `listings` has a row for each directory listed, keyed by its id. How much the tables list is declared in an optional `[sandbox.served_bytes]` table of `platform.toml` (`max_files`, `max_directories` and `max_ranges_per_file`, 1000, 1000 and 64 by default, each refused at load unless an integer of at least 1), every snapshot records the caps in effect (`caps`), and a declared table is in the campaign fingerprint, so a resume under other caps is refused. A table a cap cut says so, and `served.lookup_file`, `lookup_bytes` and `lookup_directory` read it by one rule: a file a cap left out is unknown, never not served or 0 bytes, and so is a byte past the last range a cut row lists. A mount's reads, which no gate sees, are unknown; a run with no data path read zero; a log that may lack a line makes every count and every table unknown, never zero or a part, and a log counts as whole only when it ends with the gate's own `teardown_complete` mark and the gate's output was read. The live tests (`tests/live/test_sandbox.py`, with `EXPCORE_LIVE_LISTING_PATH`) check this and the complete listing against a federation; they have not been run.

The factory decides which models it serves and hands the others to `default_backend_factory`. A model whose backend the core does not build is refused when the plugin is loaded, naming `models.toml` and the key, unless the plugin supplies a factory, and the core's own factory refuses to build it. - A harness defect's traceback, which the attempt does not keep, goes to a local log, `out/logs/harness-errors.log`: one entry per defect, whether the executor raised it or the loop caught it, headed by the run key, the attempt and the stack hash the marker, the record and the store hold, redacted with the attempt's whole redaction context (`RunRequest.defect_log`, which `record_run` hands to `record_attempt` and the loop's new `on_defect`), and withheld with the reason when a secret is too short to redact. An entry that cannot be written never costs the record or the marker: the failure is kept, and once the result is stored dispatch stops loudly, naming the log. The loop guards any sink the same way: what an executor's own sink raises is carried on the result (`LoopResult.sink_failure`), handed on once the record is built (`record_attempt`'s `on_sink_failure`, which `record_run` points at the attempt's log) and reported the same way. The directory ignores itself for git (a `.gitignore` the author put there is kept, and ends with the line `/harness-errors.log`, which the last-rule-wins order makes ignore the log whatever came before), a replication package never selects it whatever its patterns, and `run` prints the log's path when harness errors stop dispatch. The plugin's "failed on import" message on `run` and `analyze` shows the exception's text redacted as a record is, the keys `models.toml` points at included, redacting a value too short to replace everywhere only where it stands as a token of its own (so it cannot wipe the diagnostic, while a record refuses it), and names the log, where that failure's traceback goes too.

- Price tiers by prompt length in `models.toml`: two or more `[[models.<key>.price.tiers]]` tables in place of the flat prices, each with its input, output and cache prices, and every tier but the last with `up_to_prompt_tokens`, the longest prompt it takes. A request, its reply included, takes the prices of the tier its prompt fell in. The store keeps each turn's usage (`attempts.turn_usage`, and the marker's `turn_usage`), and the cost measure prices a tiered model request by request from it, so a run's cost is what its record gives. A model without tiers is priced from its totals as before, with an unchanged entry and campaign fingerprint.
- The budget reserves for each run the most its caps let it cost, which is tighter than before for a backend that caps its replies and now covers the request a run can make past its token cap. The cap counts each reply's input and output, and the loop checks it before each request, so a run can pass it by one request, whose prompt the context window bounds. For a model held to its reply maximum (below), the requests within the cap are reserved at most the rounds times the reply maximum as output and the rest of the cap as input, at the dearest rates of any tier, and the request past the cap the context window at the input rate and one reply at the output rate. For any other model, the stub and a study's own backend among them, the whole cap at the dearest rate, as before, and the whole window at the dearest rate; a stub's scripted usage beyond the window is outside the guarantee. An attempt whose usage is unknown is charged the same bound, and a read-only snapshot of a store older than `turn_usage` is costed without it. With a budget, `run` refuses to start or resume with a planned model that is not free and declares no `context_tokens`, naming `models.toml` and the key; checking, analysing, reporting and a package's check of a finished study do not need it.
- The reply maximum bounds a run's reservation only where the campaign has shown the endpoint holds replies to it (C27): the core's own factory builds the model's OpenAI-compatible or Anthropic adapter, and with a budget, at each start, admission sends a request with a `max_tokens` of 16 that asks for a long reply, which must come back cut at that limit. Any other model, one a plugin's factory builds whatever its `backend` included, is reserved by its context window, and a model the probe does not show is admitted with a `reply_cap_not_shown` event. A reply that later reports more than the maximum is a `reply_over_maximum` event and takes the model off it for the rest of the campaign: its runs are reserved by the window from then on, those in flight too, and a later request of a run reserved by the maximum goes out only while the campaign is within its ceilings. Which bound a run was reserved is the decision of the assessment that admitted it, carried into its spend guard and recorded on its attempt's row (`attempts.reserved_capped`), so an attempt whose usage is unknown is charged that bound at every later start, before admission has run too, unless its model was taken off the maximum since; and every resend is cleared again right before it goes out, after the retrier's wait: a top-up reserved by the maximum before the wait reserves the rest of its bound by the window if the model was taken off it meanwhile, or the resend is not sent.
- Top-ups for the sends a run's token cap cannot account for (C26): a resend after a connection error or a 5xx, and every request after a reply that left its input or output count out. Each reserves one request's bound against the ceilings before it goes out, under the dispatcher's locks, and is charged at once and never refunded; the last failed send of a request is charged too. A top-up that does not fit is not sent, and the attempt ends as a budget hold: infrastructure of the new core kind `budget_hold`, set aside, never a treatment, not charged an attempt, and counted per condition and model in the export's new `budget_holds` and in a table of the report, `Budget holds by condition and model`, with a row of zeros for each pair the plan runs, so the analysis sees whether they cluster by model. A hold is counted by its attempt's own kind, so an outage that overlapped it, which `retries_by_kind` counts it under, does not hide it. A reply without usage is a `usage_unreported` event. Admission's probes are paid from the budget the same way, at every start: each send of the one-token completion and of the probe of the reply maximum, retries included, reserves one request's bound by the window before it goes out and is charged in the store (`probe_spend_usd`), an answered one settled to what its reply's counts cost; a probe the budget cannot cover is not sent and its model is not admitted, with a reason saying the budget is spent, and a start takes a release before its probes ask for room. The loop's counting and `token_cap` are unchanged; without a budget nothing is topped up.
- Admission refuses a model whose one-token completion does not report its input and output tokens (B07), budget or none: the token budget is held from those counts, so the cap would not bind that model alone.

- A study declares the side files of its records in `study.toml`: each `[[study.side_files]]` table names a file a run writes beside its record (`pattern`, one literal file name) and the record field that holds its SHA-256 (`hash_field`, a dotted path), validated at load with errors naming the file and the key. `check` hashes every file of a declared name in the batch it parses into its inputs, never replays one, and pairs each with the one record in its directory: a record naming a missing side file, a side file changed or swapped, one in a directory with no record, one beside a record that names no hash for it, and a hash that is not 64 lower-case hex digits each fail the check at stage `side_file`. The check records the declaration (`side_files`); `analyze`, `report`, `regenerate` and a package's `make check` refuse a check made under another, refuse a side file changed, removed or added since, and pair each side file with its record again. A package includes every side file and `PACKAGE.json` records the declaration. The declaration is in `study.toml`, so the campaign fingerprint refuses a resume under another. A study that declares none is checked as before, and its check file and `PACKAGE.json` hold no `side_files`. `verify_batch`, `require_current_check` and `study.verified.load_verified` gain a `side_files` argument.
- A scorer reads a side file's content as the bytes the loader verified, never by path (#144). A scorer, or a plain function used as one, that declares a `side_files` parameter is passed the record's side files as a read-only mapping from declared pattern to bytes; one that takes only the record is called as before, and the example's outputs keep their bytes. `analyze`, `report`, `regenerate` and a package's `make check` hand over the bytes `load_verified` read once and paired against the replay check, before the plugin is loaded, so a side file that no longer matches is refused before any scorer runs; `rescore_files` takes the study's declaration (`side_files`) and pairs the side file beside the record of an attempt directory the same way. The same batch gives the same scores through each, byte for byte. A record with no side file gives an empty mapping, and a caller that hands over none refuses such a scorer. A side file holds at most 64 MiB (`replay.side_files.MAX_SIDE_FILE_BYTES`): `check` fails a larger one at stage `side_file`, and the loader refuses one that grew past it, reading no more than one byte beyond. Neither `check` nor the comparison of a batch with its check reads a side file whole: by its declaration it is no record, so neither looks into it for one, and every hashed-only input is hashed in chunks. Any other hashed-only file is read whole, to tell whether it holds a record, only up to 64 MiB (`replay.check.RECORD_PROBE_BYTES`); a larger one is looked at by a 4 KiB prefix and refused when that prefix opens a JSON object. `rescore` gains a `side_files` argument, and `VerifiedBatch` gains `side_files` and `side_files_for`.
- The private plain list of study tokens accepts a `whole: <token>` line, which makes that token match only as an entire identifier, literal or line whatever its length, for an ordinary word that would otherwise be found inside unrelated names; the hash file renders it as `whole <scope> <sha256>`.
- The P07 check is a command, `python -m expcore.provenance.history --map MAP --source-repos "NAME=PATH;..."`: each module under `src/` that names a source must, as the commit that started its history holds it, reproduce from that source's blob under the private map. That commit is found without git's copy detection, and a merge counts when it holds the module as no parent does and its first parent lacks it, so a hand-edited copy of an imported module, or one a merge adds back edited, is checked at its own adding commit; a rename is looked for against each parent of a merge, so a module a side branch imported and the merge renamed is traced to that import. The command names a module, never a source repository, and exits 2 when there is no module to check. Section 9 of the study guide documents the sanitising import, its map, the provenance header and this check.
- A model served by several deployments can be one model (B18): its entry in `models.toml` declares `accepted_fingerprints`, the serving fingerprints of the deployments the study decided are the same model, and the set goes into the campaign fingerprint, so a resume under another set is refused. A reply served under a fingerprint of the set is accepted; one under any other still sets its run aside as a changed identity, and the served model id is checked as before. The admission probe must be served by the model under a fingerprint of the set. A declared fingerprint is confirmed by the probe or by the first run whose reply shows it, and one never shown is reported as unconfirmed. Each attempt records the turns each fingerprint served (the store's `deployments` column), and the export's `deployment_shares` and the report's "Deployments" section give, per model, each fingerprint's count and share of the analysed turns and runs and the runs served by more than one. A model without the key keeps its checks, its records, its fingerprint digest and its export; the `anthropic` backend records no fingerprint and cannot take the key.

### Changed

For readers of the commits before this release:
- `export.json` and the campaign snapshot name each attempt's directory as `<digest>/try<N>`, relative to the batch, instead of the absolute path the store keeps; the snapshot is also rebuilt so its free space holds no older copy. Neither carries a path of the machine the campaign ran on any more.
- `analyse_study` writes nothing. `write_analysis` writes `export.json`, `scores.json` and `analysis.json`, `write_report` writes `report.md`, and `regenerate` compares all four with what the records give.
- The report and the terminal summary take a contrast's exploratory label from the statistics kernel's own flag, and refuse a result whose flag disagrees with its Holm decisions. A contrast outside the Holm family is shown as exploratory in every table, never as confirmatory.
- The platform probes' snapshot is version 2, and `gained_bytes` in it is stated as placement gained: the bytes of the blocks a provider's block map shows at run end that it did not show at run start; what it showed at the start and no longer does is `lost_bytes`, kept apart, so it is not a net change, and it is not bytes on the wire. The run's end now waits on the transfer listing (`[placement] transfer_settle_s`, 30 s by default, for up to `transfer_settle_polls` observations).
- The campaign fingerprint and `replay-check.json` gain `environment`, so a store or a check made before it cannot be resumed or analysed. `PACKAGE.json` gains `environment`, `wheels`, `study_tokens_exempt`, `code_identity`, `vcs` and `uncommitted`, and the generated Makefile's `check` target installs the package's wheels; `check-installed` is the old behaviour.
- `users.SlotTokens` and `sandbox.provider.SandboxPlatform` take a required `events`, the platform's event sink, with no default, because a silent no-op would lose an event. A caller that built either without one must now pass it.
- `[toolserver] insecure_tls` and `[sandbox.mount] tls` are refused at load with a pointer to `[tls]`, which replaces both; `ToolServer.insecure_tls` and `MountSettings.tls` are gone, and the sandbox metadata's `mount` no longer holds `tls`, now the run's own `tls`. `StudyPlugin` gains `platform`, empty by default, and the campaign fingerprint gains a `platform` section only when a plugin gives one, so campaigns already started keep their fingerprint.
- A contrast in the Holm family that loses a pair to a treatment attempt scored `None` is refused. `treatment_outcomes = "excluded"` in its preregistration leaves every pair with a treatment attempt out instead; `treatment_outcomes = "scored"` claims the scorer returns values for them, and the claim is checked: such a contrast is refused too, past its preregistered `max_unscored_treatment` (0 unless set), which cannot excuse every treatment attempt. A confirmatory contrast that `"excluded"` leaves with no pair is refused too. Each contrast counts its missing pairs by cause (`pairs_missing` in `analysis.json`), and the report puts the declaration and its count in the contrast's row. - The mutation gate finds the space of a file addressed by id by walking its `parent_id` links through the provider up to the configured space's root, at most `client.MAX_SPACE_DEPTH` (64) links, instead of reading a `path` attribute, which Onedata 25.0 does not have; it then reads the space's name from Onezone before every request, as before. The roots and links a walk read are kept as the provider's that gave them, at most `client.MAX_KEPT_LINKS` (50,000) links, least recently used dropped first, all dropped by `close()`; no walk that failed keeps anything, and one that passes the bound over kept links walks once more with every link read anew before it refuses. `OnezoneClient` takes `kept_links`. `client.NotSent` is new: `OutOfScope`, `MintNotSent` and the new `ScopeUnread`, raised when one of the gate's own reads fails and keeping that read's status, error id, errno and transport flag, are all `NotSent`. - Provisioning waits until a provider sees a file written through another before it reads or schedules a transfer through it (`Provisioner.await_visible`, `consistency.wait_visible`): the file's size is read through the provider every 0.5 s until it equals the data provider's, for at most `consistency.VISIBLE_TIMEOUT_S` (120 s), past which `NotVisible`, a `WaitTimeout`, names the provider by its position. A 404 or 400 `posix` `enoent` is "not visible yet"; any other error fails closed. Placement, `fetch` and the scheduling of a replication or an eviction wait; the probes' reads never do.
- `Provisioner.evict` judges an eviction by the block map alone: while the provider still holds bytes after the transfer ended, it schedules the eviction again after `provision.EVICTION_RETRY_PAUSE_S` (10 s), up to `EVICTION_ATTEMPTS` (5), and after the last waits the settle bound and raises `NotPlaced`. On 25.0 an eviction made right after a provider fetched the bytes completes with `filesEvicted` 0. Its record gains `attempts`, and `require_empty` takes `timeout_s`.

On 25.0 a range read places at least 1 MiB from its offset, clipped to the file. - `PlatformError` gains `errno`, the POSIX code Onedata gives with the error id `posix`. `client.answered_absent` is the one test of absence: a 404 or exactly 400 `posix` `enoent`, as 25.0 answers a deleted entry, and never a request that was not sent. Teardown, its absence polls and its listing of a logged directory, `read_only`'s clean-up and the gate's walk use it, so they stop as soon as an entry reads gone; so do the consistency waits for a fresh space root and for a transfer its provider does not show yet (`consistency.NOT_FOUND` is gone). ### Known limits

- A complete listing is complete only for a directory that does not change while the gate reads it: Onedata gives a listing no snapshot. An entry another client inserts during the read makes another come twice, and the listing is refused; an entry removed during the read can shift another out of the pages unseen, and the answer lacks it with nothing to show. Entries that carry neither a file id nor a name cannot be told apart, so a repeat among them is not found.
- Threat model of the replication-package checks: they catch accidental leaks of private names and listed terms in text and in common encodings of it (UTF-16, escapes, entities, base64 and hex runs, compressed and archived content, SQLite databases). They do not defend against deliberate concealment, and they never read text inside images.
- The redaction of the package and provenance commands covers the core's own messages, not every form a name can take: a listed name of more than twelve words, or one that ends in punctuation, is not looked for as a phrase in a message; a name a message splits across a line break is not joined; and what a study's own plugin prints while it is run to regenerate the outputs is the study's code, not a core message, and is not redacted. A listed name that is an ordinary phrase can hide a whole message line, which errs on the safe side.
- A package's wheels are those of the build's platform and Python, so a reader needs the same. Every text member of every wheel is read with the study-token list, except in a wheel the study's `uv.lock` proves a pypi.org release, and in an anonymised build with the anonymisation list; a member that is not text is attested by its hash. They add about 65 MB to the example's package. An editable install cannot be packed from its installed files and needs `--wheels`; files a distribution installs outside its site directory are left out of a packed wheel, apart from the console scripts the installer writes again.
- An anonymised package still shows the distribution name `papers-experiments-core`, the module name `expcore` and the core's code; it withholds the vendored code's provenance headers. A release from an index is read as it is, without the decoded views the author's own code gets. With the core's public token list the example's package builds, plain and anonymised, with no wheel exempt and no member attested. A library whose code holds a word of the list is refused when it is packed again from its installed files, since a re-packed wheel never has the bytes of the published artifact the lock records; supplying its published wheel with `--wheels` (the file whose URL and hash `uv.lock` records) exempts it from that list, and attesting the member in `package.toml` works too.
- The package's study-token check uses the hashes whose scope is `all`, the names private everywhere (hosts, addresses, users, spaces, providers). A study's own condition, dataset and model names are expected in its own package, so code-scope hashes are not applied. `--hashes` takes another hash file, for example a study's own, in place of the core's list rather than in addition to it, and the build prints how many hashes it checks with. A hash file with a line in any other format is refused, a bare `sha256sum` digest by name, but one whose lines have the format and whose digests were made some other way cannot be told from a correct one; the study guide gives the format, the hash rule and the command that makes the file.
- Anonymisation relabels only whole words in the prose and metadata files its list names (JSON lexically, string by string, TOML and text as text; YAML is refused, since without a parser its rewrite cannot be checked), and fails the build on a listed term anywhere else, escaped or encoded forms included; it never rewrites code. The scanner and canaries of earlier packages are not in this release.
- The package's checks fail closed. A file goes in only if they can read all of it: UTF-8 text without NUL bytes, UTF-16 text with a byte-order mark, an SQLite database (its values read too), or a gzip, bzip2, xz, zip or tar archive of such files; base64 and hex runs in text are decoded and read the same way. Anything else (a PDF or PostScript file, even in ASCII, a PNG, a raw zlib stream, unknown binary, a member that fails to decompress) is refused unless `package.toml` attests that exact file by its SHA-256 with a reason in an `[[opaque]]` entry; it then goes in unscanned, on the author's word that it was inspected by hand.
- A prompt template nested in another, rendered first and passed as a slot's value, is recorded as that slot's text: the record holds the outer template's hash, and neither the inner template's hash nor its slot values ([`docs/interfaces.md`](docs/interfaces.md#prompttemplate)).
- A file an agent writes during a run has no place in the batch unless the study declares it as a side file: the replay check takes an undeclared `.json` file beside a record as a record and fails it, and hashes no undeclared file of another kind. What the scorer needs of such a file goes into the record as an instrument's snapshot ([`docs/study-guide.md`](docs/study-guide.md#files-an-agent-writes)); the original bytes are not carried.
- A study cannot register an estimator through its plugin: the preregistration is validated when the study is loaded, before the plugin is imported, so a name only the plugin registers is refused as unknown. An installed module named in `[study] platforms`, which is imported first, can register one, and the analysis then uses it ([`docs/interfaces.md`](docs/interfaces.md#estimator)).
- Not in this release: streaming transport (B17), snapshot cut and fetch (C21), confirmed model-level faults (C22), blind coding sheets (S08), the package scanner's canaries (K02) and its removal of temporary credential copies (K09), fault injection and its sanction (O10; built and reviewed in #17, held for the release-boundary decision), two-host execution, sampling for cause coding and further estimators ([`docs/architecture.md`](docs/architecture.md#release-boundary)).
