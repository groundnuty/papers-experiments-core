# Changelog

Every release of `papers-experiments-core`. Versions follow semantic versioning with tags `vMAJOR.MINOR.PATCH`; while the version is 0.x, a minor release may break interfaces, and its entry says which.

## 0.1.0 (unreleased)

The first release: what a study needs to run end to end on the core (agent loop, model backends, tools, prompts, records and replay, the campaign kernel, the statistics kernel, provenance and replication packages), with the Onedata platform layer: configuration, token planes, tool-server launch, health, the sandbox and its data paths, the data gate, provisioning and placement, platform probes, leased platform users and day-0 checks. A study depends on it by tag and copies nothing; [`docs/study-guide.md`](docs/study-guide.md) shows how. What the release guarantees is the list of regressions at the end of this entry: each has a test on this tree, named beside it, whose docstring starts with the ID. An ID of [`docs/regressions.md`](docs/regressions.md) that is not in the list is not guaranteed yet.

**Nothing in this release has run against a live Onedata deployment.** The platform layer is tested against fakes of the Onedata API and of the MCP server. The contract tests that would talk to a real deployment (`tests/live/`) skip unless `EXPCORE_LIVE_PLATFORM` names one, and they have not been run.

### Added

- The generic core, `expcore`: the agent loop with output capping and the closed outcome vocabulary; OpenAI-compatible, Anthropic and stub backends with retries and the served-model check; the MCP stdio client with frozen manifests and allow-lists; prompt templates with named slots; records, offline replay and the replay check; the campaign kernel (factor schema, manifest, store and resume, scheduling on one host, leases, budgets, export); the statistics kernel (named contrasts, the Wilcoxon cluster-bootstrap estimator, Holm, power simulation, preregistration) and kappa for cause coding; code stamps, provenance headers and the study-token check. The interfaces a study implements are in [`docs/interfaces.md`](docs/interfaces.md).
- The platform layer, `expcore_onedata` (the `[onedata]` extra): federation configuration, both token planes with fail-closed examination, the tool-server launch with its allow-list, and health checks against the declared support set. The sandbox with its per-condition data paths (a read-only mount, REST through a data gate, or none), a data gate that holds the REST token and checks every answer before the agent sees it, ordered teardown and kill causes from kernel evidence; provisioning under configured prefixes, placement confirmed by the block map and range placement by reads, bounded consistency waits, platform probes recorded as run-end instruments, leased platform users whose slots are freed only after their tokens end, a content-type check before a campaign, and day-0 checks as code.
- Replication packages: `python -m expcore package STUDY --out DIR` builds what the study's `package.toml` lists and nothing else, with a SHA-256 manifest, a study-token check over every path and content, whole-word anonymisation lists for double-blind submissions, and a deterministic archive. The package's own `make check` (`python -m expcore package-check`) verifies every file and derives the tables and the report anew from the records, byte for byte; the build runs it before it writes anything. A package vendors one wheel per distribution of the environment its replay check ran under, and its `make check` installs them into a fresh environment with no index and no network; `PACKAGE.json` names that environment, and where each distribution came from. The study-token list applies to a vendored wheel by provenance: one whose SHA-256 the study's `uv.lock` records for that name and version from the pypi.org registry is a public release and skips that list alone, and `PACKAGE.json` lists it with the lock's hash; the core's wheel and anything installed from a URL, a repository or a directory never do. `--anonymise` also gives the package a code identity by tree hash alone: no commit id and no source URL of the study or the core, anywhere in it. Files no commit holds are warned about and listed, and refused in an anonymised build unless `--allow-uncommitted`. No message of the build, findings, warnings, hints and refusals alike, shows a path, a name or a value that holds a private name or a term: every check names such a path the same way, by the start of its SHA-256, a finding is reported once per occurrence at the file's line, and `--show-private-paths` prints the paths behind the hidden names for the author's own terminal. Any exception the build meets refuses it through the same redaction, `package-check` shows its problems through the core's public list, and no command of the core or of its provenance tools repeats an argument it does not take or prints an exception unredacted.
- The campaign's environment: the core and what `[study] requires` names, with everything they require, each with its version and, for an install from a URL, its source. It is in the campaign fingerprint, so a resume under another one is refused, and the replay check and the analysis are bound to it.
- The example study ships in the wheel: `python -m expcore example DEST` writes it into a new directory, with its README pointing at the documentation of the installed core: a link on GitHub at the commit it was installed from, when it came from a GitHub repository, and otherwise each page's path in the core's repository at that commit or at its version's tag. The core holds no URL of its own repository, which would refuse every anonymised build (K11), so the link is built from the URL the install records. `scripts/fresh_repo.py`, run by the `fresh-repo` workflow after each push to `main`, makes a new repository that depends on the core by commit and runs the example end to end from the installed package, its replication package included.
- [`docs/study-guide.md`](docs/study-guide.md): starting a study, configuration, factors and conditions, recording and replay, scoring and analysis, freezing a protocol, replication packages and which conclusions may say "no difference". Its code runs as part of the tests.
- The platform probes record every transfer of the space that started in the run's window, whoever started it: the harness, the agent through the tool plane, or a QoS requirement. Every tracked provider's listing is read until two observations in a row agree, on a window moved onto the providers' clocks by their `Date` headers. Per receiving provider the snapshot splits the gained bytes into the transfers' bytes and `on_demand_lower_bound`, a lower bound on what came on demand. The bound is reported only when every input to it is established, and is otherwise unknown with its reasons. It also rests on the listing being complete and on the transfers' byte counters not under-reporting. A leased slot whose token comes back with a later expiry than it was minted with records a `token_expiry_beyond_request` event, which names the slot by its position.
- One TLS setting for every client of a federation, `[tls]` of `platform.toml`, taken by the REST client, the data gate's upstream connection, oneclient in the mount sidecar and the MCP tool server. Verification stays on by default. `ca_file` names a CA bundle the federation's certificate chains to; every client trusts the bytes whose SHA-256 was taken at load, never the configured file, so a bundle swapped afterwards is not trusted. `insecure_tls = true` turns verification off, for disposable test federations only, and every health reading warns while it is on. Each run's sandbox metadata records the mode, with the bundle's SHA-256 under `ca_file`, and a plugin puts it in the campaign fingerprint through `StudyPlugin.platform` (`PlatformConfig.fingerprint()`), so a resume under another mode or bundle is refused. Oneclient takes the bundle through `SSL_CERT_FILE`, and the real tool server's use of it is checked only by a gated test (`EXPCORE_LIVE_TOOLSERVER`); only the live tests confirm either.
- A study plugs in a model backend of its own without editing the core: its `models.toml` entries name it with a plain lower-case `backend` value, and `StudyPlugin.backend_factory`, which `run_study` passes to the scheduler, builds it for admission and every run. The factory decides which models it serves and hands the others to `default_backend_factory`. A model whose backend the core does not build is refused when the plugin is loaded, naming `models.toml` and the key, unless the plugin supplies a factory, and the core's own factory refuses to build it. A plugin's factory must carry a `version`; its name and version are in the campaign fingerprint, so a resume under another is refused, and a study on the core's factory keeps its fingerprint. A factory whose module's file lies outside `[study] code` must declare the installed version of the distribution that owns that file (compared as versions), or the campaign is refused naming both, so changed backend code cannot resume under an unchanged version; a file nothing owns is refused, and one in `[study] code` is covered by the code identity.
- A study's conditions can declare a platform's infrastructure kind or the study's own as their treatment. `[study] platforms` in `study.toml` names modules imported before the study is validated, so the kinds they register with `register_infra_kind` are known, and a module that cannot be imported is refused, naming the file, the key, the module and the exception's type, never its text; `[study.kinds]` declares the study's own kinds, held only while that study is loaded or run (`errors.study_kinds`), so they do not outlast it, and one that is a core or a platform kind is refused. Scopes that overlap in one process are counted: each study keeps its kinds, and one name declared differently while they overlap is refused. Neither key is part of the factor schema, so a study that uses neither keeps its campaign fingerprint and schema digest.
- A harness defect's traceback, which the attempt does not keep, goes to a local log, `out/logs/harness-errors.log`: one entry per defect, whether the executor raised it or the loop caught it, headed by the run key, the attempt and the stack hash the marker, the record and the store hold, redacted with the attempt's whole redaction context (`RunRequest.defect_log`, which `record_run` hands to `record_attempt` and the loop's new `on_defect`), and withheld with the reason when a secret is too short to redact. An entry that cannot be written never costs the record or the marker: the failure is kept, and once the result is stored dispatch stops loudly, naming the log. The loop guards any sink the same way: what an executor's own sink raises is carried on the result (`LoopResult.sink_failure`), handed on once the record is built (`record_attempt`'s `on_sink_failure`, which `record_run` points at the attempt's log) and reported the same way. The directory ignores itself for git (a `.gitignore` the author put there is kept, and ends with the line `/harness-errors.log`, which the last-rule-wins order makes ignore the log whatever came before), a replication package never selects it whatever its patterns, and `run` prints the log's path when harness errors stop dispatch. The plugin's "failed on import" message on `run` and `analyze` shows the exception's text redacted as a record is, the keys `models.toml` points at included, redacting a value too short to replace everywhere only where it stands as a token of its own (so it cannot wipe the diagnostic, while a record refuses it), and names the log, where that failure's traceback goes too.
- `run` says each hold of the campaign on stderr as it begins, changes or ends, once and not at every pass of the dispatcher: the subject, the kind, the reason and when dispatch resumes (the time a unit's pause ends, the health gate's recheck interval, or that the hold does not end by itself). A pause extended while it holds is said again, once, with its new end: `Hold` gains `until`, which a change of counts as a change of the hold, and the store's hold event gives it. `Scheduler` takes an `on_hold` callable for this, and `HoldRegistry` an `on_change`.
- A second platform as an example, `examples/sparql_platform/`, built only on the documented interfaces: a distribution of its own (`sparql-platform`) with an in-process RDF store (pyoxigraph), read-only SPARQL tools whose results are capped and marked `source_truncated` when cut, a health check, an instrument that snapshots the store at each run's start and end, and an infrastructure kind registered as documented. A small study on it, with two conditions that differ in tool exposure, runs end to end with its replication package in `tests/e2e/test_sparql_platform.py`. The core takes the platform as a development dependency only; it is not in the core's wheel.
- A preregistration that makes no confirmatory claim, such as a pilot's, says so with `exploratory_only = true` and no `holm_family`. Every contrast is then exploratory, `analysis.json` says `"exploratory_only": true` and holds no Holm decision, the report shows every contrast in one exploratory table with no family table, and its summary and the terminal say that no confirmatory claim is made. An empty `holm_family` is still refused, now naming `exploratory_only`; a family beside the flag is refused too. The power study gives power at alpha only when there is no family. `analysis.json` of every study gains the key.

- Price tiers by prompt length in `models.toml`: two or more `[[models.<key>.price.tiers]]` tables in place of the flat prices, each with its input, output and cache prices, and every tier but the last with `up_to_prompt_tokens`, the longest prompt it takes. A request, its reply included, takes the prices of the tier its prompt fell in. The store keeps each turn's usage (`attempts.turn_usage`, and the marker's `turn_usage`), and the cost measure prices a tiered model request by request from it, so a run's cost is what its record gives. A model without tiers is priced from its totals as before, with an unchanged entry and campaign fingerprint.
- The budget reserves for each run the most its caps let it cost, which is tighter than before for a backend that caps its replies and now covers the request a run can make past its token cap. The cap counts each reply's input and output, and the loop checks it before each request, so a run can pass it by one request, whose prompt the context window bounds. For the OpenAI-compatible and Anthropic backends, which send the reply maximum in every request, the requests within the cap are reserved at most the rounds times the reply maximum as output and the rest of the cap as input, at the dearest rates of any tier, and the request past the cap the context window at the input rate and one reply at the output rate. For the stub and a study's own backend, which nothing holds to the reply maximum, the whole cap at the dearest rate, as before, and the whole window at the dearest rate; a stub's scripted usage beyond the window is outside the guarantee. An attempt whose usage is unknown is charged the same bound, and a read-only snapshot of a store older than `turn_usage` is costed without it. With a budget, `run` refuses to start or resume with a planned model that is not free and declares no `context_tokens`, naming `models.toml` and the key; checking, analysing, reporting and a package's check of a finished study do not need it.
- The private plain list of study tokens accepts a `whole: <token>` line, which makes that token match only as an entire identifier, literal or line whatever its length, for an ordinary word that would otherwise be found inside unrelated names; the hash file renders it as `whole <scope> <sha256>`.
- The P07 check is a command, `python -m expcore.provenance.history --map MAP --source-repos "NAME=PATH;..."`: each module under `src/` that names a source must, as the commit that started its history holds it, reproduce from that source's blob under the private map. That commit is found without git's copy detection, and a merge counts when it holds the module as no parent does and its first parent lacks it, so a hand-edited copy of an imported module, or one a merge adds back edited, is checked at its own adding commit; a rename is looked for against each parent of a merge, so a module a side branch imported and the merge renamed is traced to that import. The command names a module, never a source repository, and exits 2 when there is no module to check. Section 9 of the study guide documents the sanitising import, its map, the provenance header and this check.

### Changed

For readers of the commits before this release:
- `export.json` and the campaign snapshot name each attempt's directory as `<digest>/try<N>`, relative to the batch, instead of the absolute path the store keeps; the snapshot is also rebuilt so its free space holds no older copy. Neither carries a path of the machine the campaign ran on any more.
- `analyse_study` writes nothing. `write_analysis` writes `export.json`, `scores.json` and `analysis.json`, `write_report` writes `report.md`, and `regenerate` compares all four with what the records give.
- The report and the terminal summary take a contrast's exploratory label from the statistics kernel's own flag, and refuse a result whose flag disagrees with its Holm decisions. A contrast outside the Holm family is shown as exploratory in every table, never as confirmatory.
- The platform probes' snapshot is version 2, and `gained_bytes` in it is stated as placement gained: the bytes of the blocks a provider's block map shows at run end that it did not show at run start; what it showed at the start and no longer does is `lost_bytes`, kept apart, so it is not a net change, and it is not bytes on the wire. The run's end now waits on the transfer listing (`[placement] transfer_settle_s`, 30 s by default, for up to `transfer_settle_polls` observations).
- The campaign fingerprint and `replay-check.json` gain `environment`, so a store or a check made before it cannot be resumed or analysed. `PACKAGE.json` gains `environment`, `wheels`, `study_tokens_exempt`, `code_identity`, `vcs` and `uncommitted`, and the generated Makefile's `check` target installs the package's wheels; `check-installed` is the old behaviour.
- `users.SlotTokens` and `sandbox.provider.SandboxPlatform` take a required `events`, the platform's event sink, with no default, because a silent no-op would lose an event. A caller that built either without one must now pass it.
- `[toolserver] insecure_tls` and `[sandbox.mount] tls` are refused at load with a pointer to `[tls]`, which replaces both; `ToolServer.insecure_tls` and `MountSettings.tls` are gone, and the sandbox metadata's `mount` no longer holds `tls`, now the run's own `tls`. `StudyPlugin` gains `platform`, empty by default, and the campaign fingerprint gains a `platform` section only when a plugin gives one, so campaigns already started keep their fingerprint.
- A contrast in the Holm family that loses a pair to a treatment attempt scored `None` is refused. `treatment_outcomes = "excluded"` in its preregistration leaves every pair with a treatment attempt out instead; `treatment_outcomes = "scored"` claims the scorer returns values for them, and the claim is checked: such a contrast is refused too, past its preregistered `max_unscored_treatment` (0 unless set), which cannot excuse every treatment attempt. A confirmatory contrast that `"excluded"` leaves with no pair is refused too. Each contrast counts its missing pairs by cause (`pairs_missing` in `analysis.json`), and the report puts the declaration and its count in the contrast's row. The example's scorer now returns values for its treatment attempts (no answer: accuracy 0, with the rounds and lookups before the failure), and its `relay-vs-baseline` declares `"scored"`. `Row.from_export` requires the export entry's `treatment` flag.
- The report gives each condition's planned runs, how each ended (analysed, exhausted, unfinished, left out) and its attempts set aside, and `analysis.json` carries the same counts under `conditions`. The infrastructure table lists every condition, with a row of zeros (kind `none`) for one that met no failure, and the report refuses an export whose run lists do not add up to `planned_runs`.
- A fifth conclusion word, `untestable`, for a contrast that used no pair, whatever the cause; such a contrast concluded `not_detected` before. It has no estimate, p-value or minimum detectable effect, even when its estimator returned numbers for no data. In the Holm family it counts as p = 1, as a NaN p-value already did, so no other contrast's adjusted p-value changes. Its report row gives the causes of its missing pairs with their counts, and the report and the terminal summary refuse a result whose word disagrees with its pairs. `conclude` takes an `untestable` flag.
- `models.toml` no longer refuses a `backend` outside `openai_compat`, `anthropic` and `stub` when the table is loaded; such a model is refused when the plugin is loaded, unless the plugin supplies a `backend_factory`. The example's executor checks that its backend has `use(script)` instead of requiring a `StubAdapter`, so a backend that wraps the stub serves it.
- Every run of a campaign is recorded with the study's whole model table (`RunRequest.models`), so the key of every model in `models.toml` is redacted from its records, whatever the backend. A key variable set to a value too short to redact now refuses a run of any model in the table, not only of its own.
- `check` reads only the `[study]` table of `study.toml` and no longer validates the study's other configuration files. It imports the study's `[study] platforms` and plugin module only when a record names a backend no native parser is registered for, and says so in one line. A record that names a kind neither the core nor `[study.kinds]` holds imports the platforms alone, also with one line. A batch that needs neither runs none of the study's code. It does not call `build`, so it needs no model or key; a parser registered only inside `build` is not found. A module that cannot then be imported refuses `check`, naming the module and the exception's type, never its text.
- A condition that names an unknown infrastructure kind is refused with the treatable kinds as its choices, instead of every known kind, and the error says how a platform's or a study's kind becomes known. A known kind that is not treatable is refused as one that can never be a treatment, whether the core, a listed platform or the study declared it.
- The example measures with an instrument. Its executor makes a fresh `FactsServed` for every run, starts it before `record_run`, finishes it after, and writes the record `finish_instruments` returns; the scorer reads the instrument's count as a fourth outcome, `served`, which is `None` when the snapshot failed. Every record of the example holds `instruments.facts`, and `scores.json` gains the outcome; the contrasts and the report's tables are unchanged.
- The README that `python -m expcore example` writes no longer links `../../docs/`, which leads nowhere outside the core's checkout, and leads with the study's own commands without `--allow-dirty`, saying where that option belongs. The command's hint says to commit the study before running it.
- Redaction also replaces a secret as Python's repr shows it and the repr of its UTF-8 bytes, each JSON-escaped and percent-encoded as the raw form is, and, in plain text that is never sealed (the harness-error log, a printed message, never a record, whose keys a common word could rename), each line of a multi-line secret of four or more characters on its own (an exception group puts `| ` between them), so `KeyError(secret)`, whose repr escapes a quote when the secret holds both kinds, leaves nothing of it in a record or the harness-error log.
- `run` reports what it dispatched as attempts of the campaign's runs (`dispatched 65 attempts of 62 runs`), not as runs, counting the attempts it began (`RunSummary.attempts`, from the store's attempt rows), so a worker that got no lease or found a gate closed once it had one is not counted. A refusal on the command line names the command (`report refused: ...`), and the analysis's refusals no longer begin with "refusing to analyse".
- A replay that finds a recorded reply the model's raw reply does not give names the part in plain words: `the recorded tool call does not match the model's raw reply in that turn (transcript[k].native): the record was changed after it was written, or the backend now reads that reply differently`, in place of a sentence about the "neutral turn" and the "native message". The study guide says what replay compares.
- An entry of `models.toml` whose backend the core does not build, and that has a problem of its own, says first that the core does not build that backend and that the plugin must supply a `backend_factory`, whatever key fails next (one of the wrong type or an unknown one included), so `backend = "toy"` with no `api_id` no longer reads as only a missing `api_id`. A refusal that names a backend close to one of the core's, a model of `campaign.toml` that `models.toml` does not define, or a model name the table cannot resolve adds the closest name (`did you mean ...?`), and the campaign's error lists the models `models.toml` defines. A condition that leaves a factor out is refused with that factor's levels.
- Both contrast tables of `report.md` gain a `Margin` column, the preregistered equivalence margin, and the interval at 1 - 2 alpha it is compared with (`90% equivalence interval` at alpha 0.05, `97.5%` at 0.0125: a level keeps every digit it has, up to ten significant ones, and the reported interval's level is named the same way), beside the interval at the reported level, so `equivalent` and `trivial_difference` can be checked from the report; a contrast without a margin shows `-` in both. Every report changes with them, so a package built before this change no longer regenerates its `report.md`; `analysis.json` is unchanged.
- The replay check's write-back redacts nothing: it checks a record's canonical form only, so a record written under earlier redaction rules writes back to itself. A record that holds a value of the checking environment's secrets stops the check at a stage of its own, `secret`, naming where, instead of failing the write-back. The replay itself redacts nothing, as before.
- `analysis.json` of every study gains `exploratory_only`, false unless the preregistration says true, so an `analysis.json` written before no longer regenerates byte for byte.
- `BudgetGate`, `attempt_costs` and `bound_usd` take the campaign's `Limits` in place of the token budget, and the store's attempts and the outcome marker gain `turn_usage`. A study with a budget adds `context_tokens` to each model that is not free, which changes that model's entry in the campaign fingerprint, so a campaign opened before cannot be resumed and starts afresh; its records still analyse. The example's models declare a context window.
- `python -m expcore.tools.manifest freeze OUT --pass-env NAME -- COMMAND` works as its usage shows: the options may follow the file, and everything after the first `--` is the server's command. A server command must now follow `--`.

### Known limits

- Threat model of the replication-package checks: they catch accidental leaks of private names and listed terms in text and in common encodings of it (UTF-16, escapes, entities, base64 and hex runs, compressed and archived content, SQLite databases). They do not defend against deliberate concealment, and they never read text inside images.
- The redaction of the package and provenance commands covers the core's own messages, not every form a name can take: a listed name of more than twelve words, or one that ends in punctuation, is not looked for as a phrase in a message; a name a message splits across a line break is not joined; and what a study's own plugin prints while it is run to regenerate the outputs is the study's code, not a core message, and is not redacted. A listed name that is an ordinary phrase can hide a whole message line, which errs on the safe side.
- A package's wheels are those of the build's platform and Python, so a reader needs the same. Every text member of every wheel is read with the study-token list, except in a wheel the study's `uv.lock` proves a pypi.org release, and in an anonymised build with the anonymisation list; a member that is not text is attested by its hash. They add about 65 MB to the example's package. An editable install cannot be packed from its installed files and needs `--wheels`; files a distribution installs outside its site directory are left out of a packed wheel, apart from the console scripts the installer writes again.
- An anonymised package still shows the distribution name `papers-experiments-core`, the module name `expcore` and the core's code; it withholds the vendored code's provenance headers. A release from an index is read as it is, without the decoded views the author's own code gets. With the core's public token list the example's package builds, plain and anonymised, with no wheel exempt and no member attested. A library whose code holds a word of the list is refused when it is packed again from its installed files, since a re-packed wheel never has the bytes of the published artifact the lock records; supplying its published wheel with `--wheels` (the file whose URL and hash `uv.lock` records) exempts it from that list, and attesting the member in `package.toml` works too.
- The package's study-token check uses the hashes whose scope is `all`, the names private everywhere (hosts, addresses, users, spaces, providers). A study's own condition, dataset and model names are expected in its own package, so code-scope hashes are not applied. `--hashes` takes another hash file, for example a study's own, in place of the core's list rather than in addition to it, and the build prints how many hashes it checks with. A hash file with a line in any other format is refused, a bare `sha256sum` digest by name, but one whose lines have the format and whose digests were made some other way cannot be told from a correct one; the study guide gives the format, the hash rule and the command that makes the file.
- Anonymisation relabels only whole words in the prose and metadata files its list names (JSON lexically, string by string, TOML and text as text; YAML is refused, since without a parser its rewrite cannot be checked), and fails the build on a listed term anywhere else, escaped or encoded forms included; it never rewrites code. The scanner and canaries of earlier packages are not in this release.
- The package's checks fail closed. A file goes in only if they can read all of it: UTF-8 text without NUL bytes, UTF-16 text with a byte-order mark, an SQLite database (its values read too), or a gzip, bzip2, xz, zip or tar archive of such files; base64 and hex runs in text are decoded and read the same way. Anything else (a PDF or PostScript file, even in ASCII, a PNG, a raw zlib stream, unknown binary, a member that fails to decompress) is refused unless `package.toml` attests that exact file by its SHA-256 with a reason in an `[[opaque]]` entry; it then goes in unscanned, on the author's word that it was inspected by hand.
- Not in this release: streaming transport (B17), snapshot cut and fetch (C21), confirmed model-level faults (C22), blind coding sheets (S08), the package scanner's canaries (K02) and its removal of temporary credential copies (K09), fault injection and its sanction (O10; built and reviewed in #17, held for the release-boundary decision), two-host execution, sampling for cause coding and further estimators ([`docs/architecture.md`](docs/architecture.md#release-boundary)).
