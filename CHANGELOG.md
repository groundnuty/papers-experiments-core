# Changelog

Every release of `papers-experiments-core`. Versions follow semantic versioning with tags `vMAJOR.MINOR.PATCH`; while the version is 0.x, a minor release may break interfaces, and its entry says which.

## 0.1.0 (unreleased)

The first release: what a study needs to run end to end on the core (agent loop, model backends, tools, prompts, records and replay, the campaign kernel, the statistics kernel, provenance and replication packages), with the Onedata platform layer: configuration of one space or several, token planes, tool-server launch, health, the sandbox and its data paths, the data gate, provisioning and placement, a complete reset between runs, platform probes, leased platform users, fault injection with target-matched treatment and day-0 checks. A study depends on it by tag and copies nothing; [`docs/study-guide.md`](docs/study-guide.md) shows how. What the release guarantees is the list of regressions at the end of this entry: each has a test on this tree, named beside it, whose docstring starts with the ID. An ID of [`docs/regressions.md`](docs/regressions.md) that is not in the list is not guaranteed yet.

**The live contract tests have run against one throwaway deployment, and only the platform layer's REST paths have been exercised on it.** The platform layer is tested against fakes of the Onedata API, of the MCP server and of the Compose services the fault injector stops and starts, and the contract tests in `tests/live/` skip unless `EXPCORE_LIVE_PLATFORM` names a deployment, the one that takes a provider down also unless `EXPCORE_LIVE_FAULTS=1`. They have run against the Compose federation of `deploy/compose-federation` (Onedata 25.0), whose dated day-0 reports and facts files are beside it. On that release they pass, the day-0 checks `read_only` and `round_trip`, which change state, included (the outage check `provider_outage` has not run there yet): the mutation gate finds a file's space, the pre-campaign content check measures, and provisioning creates, places, reads back, evicts and tears down. The fault injector's live test, the sandbox and tool-server tests have not run against a live deployment, and a probe of the mount data path could not make its mount there.

### Added

- The record says whether the attempt was held to the reservation R (#193, C27): two optional booleans at the end of the totals of `expcore-record/3`. `totals.reserved_capped` is the bound the budget gate reserved the run by, the value the campaign store keeps in the attempt's row (True: the reply maximum, False: the window), and `totals.reply_cap_unheld` is whether the store had taken the attempt's model off the reply maximum when the loop ended. False means the model was not marked when the loop ended, not that it was shown to hold the reply maximum: a model never probed (a stub, or a plugin's own factory) is also False. `RunRequest` carries both (`reserved_capped`, `reply_cap_unheld`) and `record_run` writes them; each is left out when no gate decided it, as in a campaign without a budget, so a scorer reads the bound from the record and never opens the store. Records written before this have neither and replay to their own bytes; `tests/data/record-v3/05-reserved-capped.json` pins the fields.
- The federation's Onedata build, recorded (#186): the images `deploy/compose-federation` pins are a 25.0 development build, not the released 25.0 tag (op-worker `f118ed9`, 81 commits after the tag; oz-worker `14b5bda`, 46 commits after it). `deploy/compose-federation/day0/2026-11-12-federation-facts-build.md` gives each component's commit and names the earlier dated files whose "25.0" means this build; the "Onedata 25.0" of the live-test paragraph above means it too.
- `expcore.campaign.shard` (#154): the interface for running one campaign as N shards on different hosts. The partition by pair, the shard spec and its operator-chosen label, the shares of caps and budget, the environment identity's form, and the names of what a shard records and a merge writes. Running, merging and reporting shards build on it.
- `run STUDY --shard i/N [--shard-label L [--shard-label-wide]]` (#154) runs shard i of N of one campaign on one host: the pairs of tasks, models and seeds assigned to it, each run at its place in the whole plan, on its share of every unit cap and budget ceiling, with the campaign fingerprint of the whole plan. The store pins the shard spec, its first start, its environment identity (`StudyPlugin.environment_identity`, read once when the shard starts) and its shares; a resume refuses another spec, label or rule, a shard resumed without `--shard` or the reverse, a changed identity or changed shares, and the plan of a shard never grows on resume. The label is 1 to 64 of `[a-z0-9-]` with no dot, so a host name or an address is refused; `--shard-label-wide` allows `.` and `_`. A shard says its environment as it starts: one block of the digest of the fingerprint's environment section and its distributions, so a host that would not merge shows before it runs. A shard's export has a `shard` object. A total below the shard count, or a shard with no run, is refused at start. Without `--shard` the store, records, export and report are byte for byte what they were. The study guide's section "Running one campaign on several hosts" explains the partition, the shares and their trade-off, and the identity.
- `python -m expcore merge OUT SHARD_OUT...` (#154): the outputs of a campaign's shards, merged into one batch under `OUT` (normally the study's `out/`): `OUT/runs` holds the union of the shards' runs, `OUT/shards/<index>/campaign-snapshot.sqlite` each shard's snapshot of its store, and `OUT/merge.json` (`expcore-merge/1`) the shards, their start times, shares and run counts, and the SHA-256 of each snapshot. It refuses, naming the shard and the reason, shards that differ in rule or count, lack an index or repeat a label, have different campaign fingerprints, overlap, hold a run that belongs to another shard or leave a run of the plan out, fail their own replay check, or recorded different environment identities (C29). `check`, `analyze`, `report`, `regenerate` and `package` then work on the merged batch as on any other: `check` binds merge.json by its hash and compares each snapshot with the hash it names, `check` and `analyze` each rebuild merge.json from the snapshots and the study's plan through the merge's own checks and refuse a file that differs, the batch's export is the shards' exports joined in plan order with each run entry tagged `"shard": index` and a top-level `"shards"`, and its scores, analysis and report equal those of one driver of the whole campaign, apart from the fields of a shard's own dispatch sequence and the witness named for a deployment fingerprint two shards both confirmed (the first shard's, where one driver names the earliest). The export of an unmerged batch is unchanged.
- Sharding a campaign by model (#154, C32): `[shards] per_model = { model-a = 20, model-b = 6 }` in `campaign.toml`, for a campaign that runs one platform per concurrent run and so has far more shards than a model has concurrent sessions. N is the sum, and `--shard i/N` must give it; shard i serves one model, the models in declared order, that model's pairs are dealt among its own shards as before, so a pair stays whole, and each shard runs one run at a time, so a model's count is its concurrent sessions. The layout is in the campaign fingerprint, and the stores pin the rule `expcore-shard/3`. A model's `per_model_usd` is split over its shards, and `max_usd` over the priced models' shards in proportion to each one's planned runs times one run's reservation, in micro-dollars rounded down, so the parts never sum past it; a free model's shards get nothing. Refused when the study loads: a count above its unit's cap, a model without a count, and a budget that cannot pay one run's reservation for every priced shard. Under either rule, a shard holding pairs of a model whose concurrency share is 0 is refused at start, naming the model. The merge checks each run by the shards' own rule, so shards made under `expcore-shard/2` still resume and merge, and a campaign split by model and merged gives the scores and analysis of one driver, byte for byte, also when only some of its models declare accepted fingerprints (the shards' exports then differ in `deployment_shares`, and a shard without it counts as no entries). Without `[shards]` nothing changes.
- The report of a merged, sharded campaign (#154): when the batch's export has `shards`, `report.md` gains a `## Shards` section with a row per shard and condition (label, start, runs planned, analysed, exhausted, unfinished and left out, and the shares of the planned runs that ended analysed, exhausted and unfinished), so a reader can see whether outcomes differ by host, and two more tables: the infrastructure attempts by shard and kind, and the wall time, turn latency and reset time by shard (median and 90th percentile with N). The merged export carries what they need, and only it does: a top-level `shard_retries_by_kind` (each shard's own `retries_by_kind` rows tagged with `shard`), and `wall_s` and `turn_latency_s` in each analysed entry (the attempt's wall time from its shard's snapshot, and each turn's latency in order from the verified record). The reset time is recorded nowhere in the core, so it reads `not recorded`, as does any figure an export lacks. The shards are a check that hosts are interchangeable, not a factor of the design: every figure is descriptive, no test across them is made, and no score is shown by shard. The export and report of an unmerged batch, and the export of a shard on its own, are byte for byte unchanged.
- The generic core, `expcore`: the agent loop with output capping and the closed outcome vocabulary; OpenAI-compatible, Anthropic and stub backends with retries and the served-model check; the MCP stdio client with frozen manifests and allow-lists; prompt templates with named slots; records, offline replay and the replay check; the campaign kernel (factor schema, manifest, store and resume, scheduling on one host, leases, budgets, export); the statistics kernel (named contrasts, the Wilcoxon cluster-bootstrap estimator, Holm, power simulation, preregistration) and kappa for cause coding; code stamps, provenance headers and the study-token check. The interfaces a study implements are in [`docs/interfaces.md`](docs/interfaces.md).
- The platform layer, `expcore_onedata` (the `[onedata]` extra): federation configuration, both token planes with fail-closed examination, the tool-server launch with its allow-list, and health checks against the declared support set. The sandbox with its per-condition data paths (a read-only mount, REST through a data gate, or none), a data gate that holds the REST token and checks every answer before the agent sees it, ordered teardown and kill causes from kernel evidence; provisioning under configured prefixes, placement confirmed by the block map and range placement by reads, bounded consistency waits, platform probes recorded as run-end instruments, leased platform users whose slots are freed only after their tokens end, a content-type check before a campaign, and day-0 checks as code.
- Replication packages: `python -m expcore package STUDY --out DIR` builds what the study's `package.toml` lists and nothing else, with a SHA-256 manifest, a study-token check over every path and content, whole-word anonymisation lists for double-blind submissions, and a deterministic archive. The package's own `make check` (`python -m expcore package-check`) verifies every file and derives the tables and the report anew from the records, byte for byte; the build runs it before it writes anything. A package vendors one wheel per distribution of the environment its replay check ran under, and its `make check` installs them into a fresh environment with no index and no network; `PACKAGE.json` names that environment, and where each distribution came from. The study-token list applies to a vendored wheel by provenance: one whose SHA-256 the study's `uv.lock` records for that name and version from the pypi.org registry is a public release and skips that list alone, and `PACKAGE.json` lists it with the lock's hash; the core's wheel and anything installed from a URL, a repository or a directory never do. `--anonymise` also gives the package a code identity by tree hash alone: no commit id and no source URL of the study or the core, anywhere in it. Files no commit holds are warned about and listed, and refused in an anonymised build unless `--allow-uncommitted`. Every build, the plain one included, writes each `key_file` and `key_env` of `models.toml` as a fixed placeholder, changing no other byte, and refuses a package whose `models.toml` still holds another, one in which any file, or any wheel not from an index but the core's, still names a key location the study's models declare (wherever no part of a path continues it, and a bare file name only quoted or after a `/`; a library that names the same variable by chance is attested in `[[opaque]]`), one that packages a declared key file itself, and a second file named `models.toml`; where a key lives is outside the code identity and the campaign fingerprint, so the shipped file verifies as it is, and moving a key never stops a campaign from resuming. A key location written where that rewrite cannot reach it (an inline table, a dotted key, a multi-line string), and a `models.toml` that is not TOML as its bytes are, are refused when `models.toml` is loaded and when it is hashed. No message of the build, findings, warnings, hints and refusals alike, shows a path, a name or a value that holds a private name or a term: every check names such a path the same way, by the start of its SHA-256, a finding is reported once per occurrence at the file's line, and `--show-private-paths` prints the paths behind the hidden names for the author's own terminal. Any exception the build meets refuses it through the same redaction, `package-check` shows its problems through the core's public list, and no command of the core or of its provenance tools repeats an argument it does not take or prints an exception unredacted.
- The campaign's environment: the core and what `[study] requires` names, with everything they require, each with its version and, for an install from a URL, its source. It is in the campaign fingerprint, so a resume under another one is refused, and the replay check and the analysis are bound to it.
- The example study ships in the wheel: `python -m expcore example DEST` writes it into a new directory, with its README pointing at the documentation of the installed core: a link on GitHub at the commit it was installed from, when it came from a GitHub repository, and otherwise each page's path in the core's repository at that commit or at its version's tag. The core holds no URL of its own repository, which would refuse every anonymised build (K11), so the link is built from the URL the install records. `scripts/fresh_repo.py`, run by the `fresh-repo` workflow after each push to `main`, makes a new repository that depends on the core by commit and runs the example end to end from the installed package, its replication package included.
- [`docs/study-guide.md`](docs/study-guide.md): how to build a study on the core, from starting one to its replication package, and how to write a platform of your own. Its code runs as part of the tests. Its last section lists what a platform shipped as a distribution of its own needs (`[study] requires`, `[study] platforms` with `register_infra_kind`, `StudyPlugin.platform`, `health_kind`, and vendoring its wheel) and points at `examples/sparql_platform/`.
- [`docs/interfaces.md`](docs/interfaces.md) states what a tool author otherwise learns from the examples: the calling convention of `FunctionProvider` (`(ToolSpec, function)` pairs, `f(arguments, *, timeout_s)`, `ctx` only when declared, a `str` or a `ToolOutput`, a worker thread), `tools_sha256` and how it differs from the hash a record carries, how `record_run` combines several providers (a tool name offered twice is refused, never shadowed), and what each field of `ToolOutput` means, including how a platform's own cut differs from the core's character cap.
- The platform probes record every transfer of the space that started in the run's window, whoever started it: the harness, the agent through the tool plane, or a QoS requirement. Every tracked provider's listing is read until two observations in a row agree, on a window moved onto the global clock, the one a job's times are stamped on, which Onezone's public current-time endpoint reads (#207); a job cancelled before it started is never recorded, since it has no finish time and the listing's walk stops at it, and it moved no bytes. Per receiving provider the snapshot splits the gained bytes into the transfers' bytes and `on_demand_lower_bound`, a lower bound on what came on demand. The bound is reported only when every input to it is established, and is otherwise unknown with its reasons. It also rests on the listing being complete and on the transfers' byte counters not under-reporting. A leased slot whose token comes back with a later expiry than it was minted with records a `token_expiry_beyond_request` event, which names the slot by its position.
- Fault injection (`expcore_onedata.faults`, O10 and O11): a sanctioned injector takes a named provider down for a run and restores it, a restore counting only when the provider's identity changed and the provider serves (its container healthy, when it has a health check, and the platform's authenticated REST read through it answered, within `ready_timeout_s` of `[faults]`, 180 s by default; the wait is recorded as `ready_after_s`, and a provider that does not serve in time leaves the injection open), with a durable journal that the next start recovers, which waits for the provider to serve too, and, for an injection a process was killed in while its stop command blocked (the journal says `stopping` before the command), waits for the provider to show down before it judges the restore. Outage runs are exclusive with every other run through a federation reader-writer lock, and the platform's health gate admits no run while an injection is unsettled. Treatment is matched to the target: a condition may declare `{kind, target}`, and an attempt is treatment only when its error names that target, the injector recorded injecting it in that attempt, and the model completed a turn. The injector's kinds, `provider_outage` and the untreatable `injector_failure`, are registered by the platform layer's one module of kinds, `expcore_onedata.sandbox.kinds`, which a study lists in `[study] platforms`. With `[faults]`, the platform's half of the campaign fingerprint (`PlatformConfig.fingerprint()`) gains the sanction and each target's service, by the target's label and the SHA-256 of the service's name, so a resume that adds or drops `[faults]`, changes the sanction or takes another service down is refused; a platform.toml without `[faults]` keeps its fingerprint.
- Matched isolation for fault studies (O11): a condition may declare `exclusive = true` in the factor schema, with no fault, and its runs then hold the federation exclusively, as an outage run does, so a control can run under the same isolation as the outage it is compared with. The setting is validated at load, and a campaign whose platform gives no run admission (on Onedata, a platform.toml without `[faults]`) refuses it, naming the file and the key. Each attempt stores the admission it actually held as it was admitted (`shared`, `exclusive`, or `none` for a study without admission) and the export carries it in every analysed, excluded and exhausted entry (`admission`, `admissions`).
- One TLS setting for every client of a federation, `[tls]` of `platform.toml`, taken by the REST client, the data gate's upstream connection, oneclient in the mount sidecar and the MCP tool server. Verification stays on by default. `ca_file` names a CA bundle the federation's certificate chains to; every client trusts the bytes whose SHA-256 was taken at load, never the configured file, so a bundle swapped afterwards is not trusted. `insecure_tls = true` turns verification off, for disposable test federations only, and every health reading warns while it is on. Each run's sandbox metadata records the mode, with the bundle's SHA-256 under `ca_file`, and a plugin puts it in the campaign fingerprint through `StudyPlugin.platform` (`PlatformConfig.fingerprint()`), so a resume under another mode or bundle is refused. Oneclient takes the bundle through `SSL_CERT_FILE`, and the real tool server's use of it is checked only by a gated test (`EXPCORE_LIVE_TOOLSERVER`); only the live tests confirm either.
- A REST data path can serve complete listings. `[sandbox.data_paths]` takes a table for a level, `level = { kind = "rest", listing = "complete" }`, and that level's data gate answers every listing with all of the directory's entries, in the server's order, as one last page; it follows the pages upstream itself, so a client that reads one page (the official client's `ls`) sees the whole directory. It fails closed: a page that neither ends nor continues the listing, gives a key twice, or gives a token or an entry the listing gave before, or a page after the first that is not a 200, is the platform's 502; a listing whose entries and tokens pass 64 MiB, or that passes 10,000 pages, is refused for the gate's integrity (`listing_too_large`), so its run is set aside; a listing that names where it starts is the agent's 400. A study selects the mode per condition through the level, and the run's metadata (`listing`) and `PlatformConfig.fingerprint()` record it. The earlier study's whole-file mode is not carried over.
- The bytes each run's agent read through its data path. The platform's second instrument, `ServedBytes` (namespace `served_bytes`), records the count the sandbox's collection takes once from the log of the gate it stopped: the body bytes of the platform's answers the gate served the agent, as file content, listings as served and other answers, with the gate's own answers apart. The same count comes per file and per directory, so a study can check its agent's claimed reads file by file: `files` has a row for each file whose content was served, keyed by the file id the request's path names, with that path as the gate logged it, the number of answers, the unique byte ranges served (merged, starting where the platform's answer says) with the bytes in them, and the body bytes; `listings` has a row for each directory listed, keyed by its id. How much the tables list is declared in an optional `[sandbox.served_bytes]` table of `platform.toml` (`max_files`, `max_directories` and `max_ranges_per_file`, 1000, 1000 and 64 by default, each refused at load unless an integer of at least 1), every snapshot records the caps in effect (`caps`), and a declared table is in the campaign fingerprint, so a resume under other caps is refused. A table a cap cut says so, and `served.lookup_file`, `lookup_bytes` and `lookup_directory` read it by one rule: a file a cap left out is unknown, never not served or 0 bytes, and so is a byte past the last range a cut row lists. A mount's reads, which no gate sees, are unknown; a run with no data path read zero; a log that may lack a line makes every count and every table unknown, never zero or a part, and a log counts as whole only when it ends with the gate's own `teardown_complete` mark and the gate's output was read. The live tests (`tests/live/test_sandbox.py`, with `EXPCORE_LIVE_LISTING_PATH`) check this and the complete listing against a federation; they have not been run.
- A study's executor can check the sandbox before the agent's loop without the check entering the run's evidence. `exec(code, timeout_s, record=False)` runs as the agent's user in the agent's container and is recorded under `harness_steps` in the sandbox's metadata with its exit status and the host killer's kills it met, never as one of the agent's cells; its gate refusals and kills are not put on the agent's first cell. It runs before the agent's run only, and is refused once the mark is set or an agent's cell has begun. `DockerSandbox.mark_run_start()` then marks where the agent's run begins: the gate, on SIGUSR1, writes the mark in its own log, naming each request it had begun and not yet logged, and the sandbox reads it back before it returns. The count of the bytes served, its tables and the lookups that read them take only the answers after the mark, and those before it are counted apart (`before_run_start`); the snapshot says whether a mark was set (`run_start_marked`). Without a mark everything counts, as before; a mark the log does not confirm leaves the count unknown (`run_start_unconfirmed`). The mark is refused a second time, once an agent's cell has begun (not only ended), while a harness step runs and after the collection, and an agent's cell entered while the mark is set waits for it.
- An agent on a REST data path can use the published Onedata client, `onedatarestfsspec`, as it is. The client refuses to start without a token, so the agent's environment holds `ONEDATA_TOKEN` set to a placeholder, `[sandbox] placeholder_token` (`placeholder` by default; 1 to 128 printable ASCII characters without white space), which is no credential, is in no fingerprint, and refuses the start if it equals the run's token. The client verifies TLS against the certifi bundle of the agent's image and reads none of the CA variables the sandbox sets, so on a REST data path the sandbox asks the image's interpreter where that bundle is and mounts it with the run's CA appended, as it does for each declared `trust_paths` entry; an image without certifi starts without it and the run's metadata says `not_in_image` (`certifi`), and an image that cannot say where its bundle is refuses the start. The data gate now drops every header in which the platform reads a token: besides `X-Auth-Token`, `Authorization` and `Cookie`, the deprecated `Macaroon` and `X-Onedata-Consumer-Token` and `X-Onedata-Service-Token`, which it forwarded before (the platform still read its own `X-Auth-Token` first). The client is a pinned development dependency, and a test runs it through the gate with the placeholder and the default trust; a live test does the same in a real agent and has not been run.
- A study plugs in a model backend of its own without editing the core: its `models.toml` entries name it with a plain lower-case `backend` value, and `StudyPlugin.backend_factory`, which `run_study` passes to the scheduler, builds it for admission and every run. The factory decides which models it serves and hands the others to `default_backend_factory`. A model whose backend the core does not build is refused when the plugin is loaded, naming `models.toml` and the key, unless the plugin supplies a factory, and the core's own factory refuses to build it. A plugin's factory must carry a `version`; its name and version are in the campaign fingerprint, so a resume under another is refused, and a study on the core's factory keeps its fingerprint. A factory whose module's file lies outside `[study] code` must declare the installed version of the distribution that owns that file (compared as versions), or the campaign is refused naming both, so changed backend code cannot resume under an unchanged version; a file nothing owns is refused, and one in `[study] code` is covered by the code identity.
- A study's conditions can declare a platform's infrastructure kind or the study's own as their treatment. `[study] platforms` in `study.toml` names modules imported before the study is validated, so the kinds they register with `register_infra_kind` are known, and a module that cannot be imported is refused, naming the file, the key, the module and the exception's type, never its text; `[study.kinds]` declares the study's own kinds, held only while that study is loaded or run (`errors.study_kinds`), so they do not outlast it, and one that is a core or a platform kind is refused. Scopes that overlap in one process are counted: each study keeps its kinds, and one name declared differently while they overlap is refused. Neither key is part of the factor schema, so a study that uses neither keeps its campaign fingerprint and schema digest.
- A harness defect's traceback, which the attempt does not keep, goes to a local log, `out/logs/harness-errors.log`: one entry per defect, whether the executor raised it or the loop caught it, headed by the run key, the attempt and the stack hash the marker, the record and the store hold, redacted with the attempt's whole redaction context (`RunRequest.defect_log`, which `record_run` hands to `record_attempt` and the loop's new `on_defect`), and withheld with the reason when a secret is too short to redact. An entry that cannot be written never costs the record or the marker: the failure is kept, and once the result is stored dispatch stops loudly, naming the log. The loop guards any sink the same way: what an executor's own sink raises is carried on the result (`LoopResult.sink_failure`), handed on once the record is built (`record_attempt`'s `on_sink_failure`, which `record_run` points at the attempt's log) and reported the same way. The directory ignores itself for git (a `.gitignore` the author put there is kept, and ends with the line `/harness-errors.log`, which the last-rule-wins order makes ignore the log whatever came before), a replication package never selects it whatever its patterns, and `run` prints the log's path when harness errors stop dispatch. The plugin's "failed on import" message on `run` and `analyze` shows the exception's text redacted as a record is, the keys `models.toml` points at included, redacting a value too short to replace everywhere only where it stands as a token of its own (so it cannot wipe the diagnostic, while a record refuses it), and names the log, where that failure's traceback goes too.
- `run` says each hold of the campaign on stderr as it begins, changes or ends, once and not at every pass of the dispatcher: the subject, the kind, the reason and when dispatch resumes (the time a unit's pause ends, the health gate's recheck interval, or that the hold does not end by itself; a gate closed because the check stayed deferred past `max_defer_s` is said as one that may not end by itself, with the passing check that would end it). A pause extended while it holds is said again, once, with its new end: `Hold` gains `until`, which a change of counts as a change of the hold, and the store's hold event gives it. `Scheduler` takes an `on_hold` callable for this, and `HoldRegistry` an `on_change`.
- A throwaway Onedata federation for the live tests and federation studies, `deploy/compose-federation`: a Onezone and Oneproviders in Docker Compose on the pinned images, as a layout file declares them (`federation.py --layout PATH`; by default one Onezone and three Oneproviders), with its own CA, every port on the host's loopback, brought up and taken down by one command each (`federation.py up|down`), and the `platform.toml` a fresh tester wrote for it from the guides alone. It has two resets, and a bare `reset` is refused naming both: `reset --clean` brings every space back to a synthetic baseline, ingested data removed; `reset --replicas`, for between runs, keeps every owner's data and evicts only what the mirrors hold, verified on the block maps, and refuses to evict anything unless every owner holds each of its files whole. A layout declares the Compose project, the services' ports and memory limits, each space's owner and mirrors, and the fixed users; it is checked key by key, and the Compose file is generated from it. The root lies in an allowed parent, `EXPCORE_FED_ROOT_PARENT`, which a study confined to its own directory may set.
- A second platform as an example, `examples/sparql_platform/`, built only on the documented interfaces: a distribution of its own (`sparql-platform`) with an in-process RDF store (pyoxigraph), read-only SPARQL tools whose results are capped and marked `source_truncated` when cut, a health check, an instrument that snapshots the store at each run's start and end, and an infrastructure kind registered as documented. A small study on it, with two conditions that differ in tool exposure, runs end to end with its replication package in `tests/e2e/test_sparql_platform.py`. The core takes the platform as a development dependency only; it is not in the core's wheel.
- A preregistration that makes no confirmatory claim, such as a pilot's, says so with `exploratory_only = true` and no `holm_family`. - The budget reserves for each run the most its caps let it cost, which is tighter than before for a backend that caps its replies and now covers the request a run can make past its token cap. The cap counts each reply's input and output, and the loop checks it before each request, so a run can pass it by one request, whose prompt the context window bounds. For a model held to its reply maximum (below), the requests within the cap are reserved at most the rounds times the reply maximum as output and the rest of the cap as input, at the dearest rates of any tier, and the request past the cap the context window at the input rate and one reply at the output rate. - The reply maximum bounds a run's reservation only where the campaign has shown the endpoint holds replies to it (C27): the core's own factory builds the model's OpenAI-compatible or Anthropic adapter, and with a budget, at each start, admission sends a request with a `max_tokens` of 16 that asks for a long reply, which must come back cut at that limit. Any other model, one a plugin's factory builds whatever its `backend` included, is reserved by its context window, and a model the probe does not show is admitted with a `reply_cap_not_shown` event. A reply that later reports more than the maximum is a `reply_over_maximum` event and takes the model off it for the rest of the campaign: its runs are reserved by the window from then on, those in flight too, and a later request of a run reserved by the maximum goes out only while the campaign is within its ceilings. - Top-ups for the sends a run's token cap cannot account for (C26): a resend after a connection error or a 5xx, and every request after a reply that left its input or output count out. Each reserves one request's bound against the ceilings before it goes out, under the dispatcher's locks, and is charged at once and never refunded; the last failed send of a request is charged too. A top-up that does not fit is not sent, and the attempt ends as a budget hold: infrastructure of the new core kind `budget_hold`, set aside, never a treatment, not charged an attempt, and counted per condition and model in the export's new `budget_holds` and in a table of the report, `Budget holds by condition and model`, with a row of zeros for each pair the plan runs, so the analysis sees whether they cluster by model. A hold is counted by its attempt's own kind, so an outage that overlapped it, which `retries_by_kind` counts it under, does not hide it. A reply without usage is a `usage_unreported` event. The loop's counting and `token_cap` are unchanged; without a budget nothing is topped up.

- Large files in and out of the platform without holding them (O25). `Provisioner.upload(path, source, *, content_type="application/octet-stream")` sends a local file a chunk (`[placement] chunk_bytes`, 16 MiB by default) at a time, each chunk a write at its offset through the mutation gate, and returns an `Upload` (`expcore_onedata.streamed`): the file id, the size and SHA-256, the bytes sent and what it did. Every answer must be a 206 of exactly the range asked for, of a file of the size it was read at, with exactly its bytes; the whole read has a deadline (`[placement] transfer_timeout_s` unless given), and no wait for the platform lasts longer than `request_timeout_s` or what remains of it.
- A bounded, logged retry of idempotent plumbing reads (#185, O29): `OnezoneClient.get` takes `retry`, a `ReadRetry` (`expcore_onedata.readretry`: three attempts, pauses of 2 s and 5 s, an injectable clock and sleep, and a count) or `ONE_ATTEMPT`, the default, and a read is tried again only when it timed out (an `httpx` read, connect or pool timeout), each retry on a connection of its own and within the call's `deadline_s`; a PUT, POST, PATCH or DELETE, an error answer, a connection error and a streamed read are never retried. The reads of the mutation gate, which find the target's space before every write and range read, are plumbing too: `mutate`, `read_range` and `read_content` take `gate_retry`, for those reads alone, and `space_name`, `file_space_id` and `file_space_name` take `retry`; the gate stays closed (each attempt that is answered decides, and after three timeouts nothing is sent), and each read of a streamed range's gate is given what remains of the deadline when it begins, so a gate of several reads cannot spend a multiple of it. The polls whose failure ends an operation (`replicate`, `evict`, the bulk eviction and the reset's eviction stage) and `place_ranges`'s block-map reads (`Provisioner.blocks(retry=)`) retry as well. Every call that reaches a GET names its choice, held by a table test that finds any get with a keyword or a path, the client's gated and space reads on any receiver, the waits by name, a method got by getattr, the client's own calls and the provisioner's and the layer's retrying helpers, and fails on a call it cannot classify: the provisioner's listings and metadata reads, `read_file`'s size read, the visibility wait, the gate and the polls, the reset's reads, the ingest's attribute reads and the root a day-0 mutating check writes under retry; the health gate, the placement probes and block maps, the transfer log and day-0's reading checks keep one attempt, so a stall stays a recorded stall. Each timed-out attempt is logged with its seconds, its connection (new, reused with the requests it had served, or unknown) and the next attempt's outcome, and each retry is counted: `Provisioner.reads_retried`, `reads_retried` in the reset's record and in the ingest's snapshot.
- Upload chunks of 16 MiB, each full chunk on a new connection (#186, O25): `[placement] chunk_bytes` defaults to 16 MiB (16777216; it was 64 MiB), and the new `[placement] fresh_connection_bytes`, 16 MiB by default, is the size from which a content write goes on a connection of its own. `OnezoneClient.mutate` takes `fresh`, which a client that built its own HTTP client honours by sending that one request through a one-shot client built as the pool's is (the same `[tls]`), closed when the answer is in, never on an idle connection of the pool, and `Provisioner` passes it for every body of at least `fresh_connection_bytes`, so with the defaults every full chunk of an upload is on a new connection and the remainder keeps the pool. A client given an HTTP client by its caller sends through that one. Reads keep the connection pool, but `chunk_bytes` also sizes the ranges of a whole-file read (`read_file`, `read_content`, range placement), so a read now takes 16 MiB ranges: four times as many ranges, and gate reads, per file as at 64 MiB. Why: on the 25.0 development build the Compose federation runs, a 200 MiB upload stalled at chunks of 64 and 32 MiB on reused keep-alive connections (3 of 289 reused PUTs, none of 336 on new ones; the body started and never finished, the provider closed at about 300 s), and 16 MiB and every smaller size passed every run, reused or not (`deploy/compose-federation/day0/2026-11-12-federation-facts-upload-and-stalls.md`). Each write of content is logged (logger `expcore_onedata.client`) with its size, the seconds it took and how its connection began, `new` or `reused` with the requests it had served, so a live run shows which writes were on a reused connection; the line names the provider by its position and holds no path, id or token. A live test at the default chunk size, with no override, uploads 50 MiB, reads it back by its hash and records each PUT's connection.
- Progressive ingest (#107, O27): `expcore_onedata.ingest.ProgressiveIngest`, an instrument that makes part of a dataset arrive during a run, as if its owner were still ingesting it, so a study can test whether an agent notices incomplete data before computing. A study's plan (`expcore_onedata.ingestplan.load_ingest_plan`, one TOML file per condition) names each file by a label, its path in the space, a staged source the study keeps, when it arrives, whether it is written whole or in parts over a duration, and its baseline: "complete" for a file every other condition reads (removed before the run, written back after) or "absent" for new data. `fingerprint(plans)` puts each plan's hash in the campaign fingerprint. Each part is written through the provisioner bound to the study's space and counts only when its hash, the data provider's block map and every provider that must see it agree; every step is a clock-labelled reading on the loop's clock, and every file id removed, created or restored is recorded with its label, the old and the new id, in the snapshot and a journal kept across runs. The start restores the baseline first, recovering a crashed run, and removes only files the ingest made or whose bytes are their staged source's, the file's staged source checked first in every removal, the ingest's own files included (a damaged copy leaves the file in place and fails that file's restore, which the post-run check refuses as infrastructure), each confirmed absent on every provider before its name is written again. Each file is restored on its own, so one that fails leaves no other missing, and every file id is recorded as soon as it exists, a failed upload's included. A failed start, part or restore is `ingest_failure`, a platform kind no condition may declare: the instrument's post-run check (#135, C31) refuses the attempt, which is set aside as charged infrastructure and run again whatever the executor does (`raise_if_failed` is the same check, as a second guard); a file not yet arrived when the run ends is the manipulation. The instrument claims its provisioner's change log (`Provisioner.claim_log`), refusing one another user wrote, and `teardown` refuses a claimed log. No record field changed: the snapshot is the instrument's, under `RunRecord.instruments["progressive_ingest"]`.
- A hard deadline for every cell of the agent's code (#190, O34). At its cap every process of the cell is killed, from the agent container's cgroup, so a worker in a session of its own goes too; a process still alive after `[sandbox] kill_grace_s` (1 to 60 s, 5 by default), as a read waiting in the kernel on the FUSE mount of a file only a stopped provider holds is, has the mount's FUSE connection aborted from the oneclient sidecar, and when that fails, cannot be done or frees nothing, the sandbox is stopped. Each grace is counted by the clock, and the whole escalation lasts at most `deadline.margin_s` past the cap (two graces and 20 s; when it runs out the escalation stops waiting); the sandbox's stop runs once the outcome is recorded, so its teardown neither delays the run's classification nor counts in the cell's time. Only the init's own `sleep`, identified by its pid and start time when the container started, is spared by the kill. Each step is recorded with its time in `metadata()["cell_deadlines"]`, with the outcome `killed`, `mount_aborted`, `sandbox_stopped` or `survived_kill` (the margin ran out). `launch` and `collect` settle the deadline of a cell still running before they decide, so a cell the agent loop cut at its cap, which is the cell's, still ends the run as `cell_unkillable` rather than the agent's `time_cap`. A clean kill is the agent's own time limit, as before; any other outcome makes the cell `kill_survived` and its attempt `InfraError("cell_unkillable")`, a platform kind no condition may declare, and ends the run: later cells, and the collection of a stopped run, raise that kind. Before, the kill at the cap waited 10 s for a process stuck on the mount, and the cell, the next one and the teardown waited for the read; the outage rerun of 12 Nov measured such a read still running 10 s after its kill. A gated live test (`tests/live/test_cell_deadline.py`) checks it with a provider stopped through the fault injector.

The driver reads the gate log without following a link. The reaper's copy of a dead run's output follows the same rule; a refused reap keeps that run's disks, and so its lease key, until an operator acts.
- A writing condition's tool-server token has no `api` caveat, so within the tool-server plane's spaces it is a full REST session of its user for every call the tool server makes: what the agent can ask for is bounded by the condition's tool allow-list and its frozen manifest alone. Onedata's `api` caveat could narrow the token to named operations without limiting it to data access, but which operations the tool server's calls are is not in Onedata's caveat source, and one missing entry would refuse a tool, so the token has none (#177).

### Known limits

- A complete listing is complete only for a directory that does not change while the gate reads it: Onedata gives a listing no snapshot. An entry another client inserts during the read makes another come twice, and the listing is refused; an entry removed during the read can shift another out of the pages unseen, and the answer lacks it with nothing to show. Entries that carry neither a file id nor a name cannot be told apart, so a repeat among them is not found.
- Threat model of the replication-package checks: they catch accidental leaks of private names and listed terms in text and in common encodings of it (UTF-16, escapes, entities, base64 and hex runs, compressed and archived content, SQLite databases). They do not defend against deliberate concealment, and they never read text inside images.
- The redaction of the package and provenance commands covers the core's own messages, not every form a name can take: a listed name of more than twelve words, or one that ends in punctuation, is not looked for as a phrase in a message; a name a message splits across a line break is not joined; and what a study's own plugin prints while it is run to regenerate the outputs is the study's code, not a core message, and is not redacted. A listed name that is an ordinary phrase can hide a whole message line, which errs on the safe side.
- A package's wheels are those of the build's platform and Python, so a reader needs the same. Every text member of every wheel is read with the study-token list, except in a wheel the study's `uv.lock` proves a pypi.org release, and in an anonymised build with the anonymisation list; a member that is not text is attested by its hash. They add about 65 MB to the example's package. An editable install cannot be packed from its installed files and needs `--wheels`; files a distribution installs outside its site directory are left out of a packed wheel, apart from the console scripts the installer writes again.
- An anonymised package still shows the distribution name `papers-experiments-core`, the module name `expcore` and the core's code; it withholds the vendored code's provenance headers. A release from an index is read as it is, without the decoded views the author's own code gets. With the core's public token list the example's package builds, plain and anonymised, with no wheel exempt and no member attested. A library whose code holds a word of the list is refused when it is packed again from its installed files, since a re-packed wheel never has the bytes of the published artifact the lock records; supplying its published wheel with `--wheels` (the file whose URL and hash `uv.lock` records) exempts it from that list, and attesting the member in `package.toml` works too.
- The package's study-token check uses the hashes whose scope is `all`, the names private everywhere (hosts, addresses, users, spaces, providers). A study's own condition, dataset and model names are expected in its own package, so code-scope hashes are not applied. `--hashes` takes another hash file, for example a study's own, in place of the core's list rather than in addition to it, and the build prints how many hashes it checks with. A hash file with a line in any other format is refused, a bare `sha256sum` digest by name, but one whose lines have the format and whose digests were made some other way cannot be told from a correct one; the study guide gives the format, the hash rule and the command that makes the file.
- Anonymisation relabels only whole words in the prose and metadata files its list names (JSON lexically, string by string, TOML and text as text; YAML is refused, since without a parser its rewrite cannot be checked), and fails the build on a listed term anywhere else, escaped or encoded forms included; it never rewrites code. The scanner and canaries of earlier packages are not in this release.
- The package's checks fail closed. A file goes in only if they can read all of it: UTF-8 text without NUL bytes, UTF-16 text with a byte-order mark, an SQLite database (its values read too), or a gzip, bzip2, xz, zip or tar archive of such files; base64 and hex runs in text are decoded and read the same way. Anything else (a PDF or PostScript file, even in ASCII, a PNG, a raw zlib stream, unknown binary, a member that fails to decompress) is refused unless `package.toml` attests that exact file by its SHA-256 with a reason in an `[[opaque]]` entry; it then goes in unscanned, on the author's word that it was inspected by hand.
- A prompt template nested in another, rendered first and passed as a slot's value, is recorded as that slot's text: the record holds the outer template's hash, and neither the inner template's hash nor its slot values ([`docs/interfaces.md`](docs/interfaces.md#prompttemplate)).
- A file an agent writes during a run has no place in the batch unless the study declares it as a side file: the replay check takes an undeclared `.json` file beside a record as a record and fails it, and hashes no undeclared file of another kind. What the scorer needs of such a file goes into the record as an instrument's snapshot ([`docs/study-guide.md`](docs/study-guide.md#files-an-agent-writes)); the original bytes are not carried.
- A study cannot register an estimator through its plugin: the preregistration is validated when the study is loaded, before the plugin is imported, so a name only the plugin registers is refused as unknown. An installed module named in `[study] platforms`, which is imported first, can register one, and the analysis then uses it ([`docs/interfaces.md`](docs/interfaces.md#estimator)).
- Ended transfers cannot be removed: Oneprovider 25.0's REST API offers no call that deletes one, so a run's agent can list the transfers of earlier runs, the reset's own included. The reset records instead what the listing shows, the count and the newest finish time per provider and together, so an analysis can account for it. Finding QoS requirements reads one summary per leaf of the space, because the API lists them only per entry. The day-0 checks still read the one space, so they refuse a configuration with several.
- The progressive ingest has not run on a live federation, and it lacks what the issue builds on #27 and #135: the preallocated mode (a file at its final size with only a prefix written, which waits for the live fact of what a read of an unwritten range returns), offsets anchored at the agent's first model turn rather than the instrument's start, #27's sanction, recovery machinery and exclusive admission with a matched control (a study that runs other conditions on the same owner's space must keep them apart itself until then), and optional metadata signals of an ingest in progress. A part is confirmed before the next is written, so a provider slow to show a part makes the next one late, and the reading says by how much. What a live check must show is in [`docs/interfaces.md`](docs/interfaces.md#instrument).
- An upload decides to skip or resume by reading the target back and hashing it, and verifies by reading the whole file back again, so a resumed or new upload moves its bytes about twice over the network; Onedata 25.0 exposes no checksum to compare instead. A file that changes during the upload fails the check rather than being reported. The large-file live test (`tests/live/test_contract.py`, with `EXPCORE_LIVE_MUTATE=1`) has not been run, so that a write without an offset truncates the file is the API description's word, not this release's measurement.
- The day-0 outage check has not run against a live federation; its fakes' answers while a provider is down (a read that blocks, a transfer that stays active, a tool's wording) are a stand-in's choices, not measurements, and its stand-in tool server relays the four tools to the fakes, so the real server's arguments and answers are read only from its own input schema and its text. A tool whose required argument the check cannot fill from its schema is not called and leaves the check unknown.
- Not in this release: streaming transport (B17), snapshot cut and fetch (C21), confirmed model-level faults (C22), blind coding sheets (S08), the package scanner's canaries (K02) and its removal of temporary credential copies (K09), two-host execution, sampling for cause coding and further estimators ([`docs/architecture.md`](docs/architecture.md#release-boundary)).
- The writing tool-server token carries no `api` caveat either. Onedata's `api` caveat could narrow the token to named operations without limiting it to data access, but which operations the tool server's calls are is not in Onedata's caveat source, and one missing entry would refuse a tool, so the token has none. What the live run showed is in O05's entry of [`docs/regressions.md`](docs/regressions.md).
- A writing condition's tool-server token ran live on 12 Nov (`deploy/compose-federation/day0/2026-11-12-federation-facts-tool-server-write.md`): in its space its replication completed and its QoS requirement was accepted, outside it both were refused, and the three reads below answered 200. The read of its user's Onezone admin privileges, `GET /users/{id}/effective_privileges`, is named by Onezone's REST description alone (`client.UNVERIFIED_ENDPOINTS`), which says its reader needs `oz_view_privileges`: an admin credential without that privilege refuses every writing token. The read of the clusters the token's user is a member of, `GET /user/effective_clusters`, is named by that description and by oz-worker's route alone (`client.UNVERIFIED_ENDPOINTS`); it is the current user's, sent as the token, since the description has no read of another user's. What the live run showed is in O05's entry of [`docs/regressions.md`](docs/regressions.md).
- A read-only condition's tool-server token is refused the transfer and QoS-requirement views by Onedata 25.0 (the live run of 12 Nov of #177, `deploy/compose-federation/day0/2026-11-12-federation-facts-tool-server-write.md`). Every write is refused and the read tools under `/data/{id}` (file distribution, QoS summary, attributes) serve, but `get_transfer`, `list_space_transfers` and `get_qos_requirement` answer 401 `tokenCaveatUnverified`, because 25.0 takes the token's `data.readonly` and `data.path` caveats, which #177 leaves as they were, as a limit to data access. The tool server's own examination of that token is refused too, so the server fails open on its write tools, which Onedata still refuses. A known gap, tracked in #181.
- A cell's deadline reaches the agent's cells only: a harness step (`exec(..., record=False)`, the start's read-only probes among them) starts no timer, and is bounded by the container's `timeout` backstop alone. The sidecar's abort of the FUSE connection (fusectl mounted in its own namespace, its SYS_ADMIN) has not run on a live federation yet; where it fails, the stop does the rest and the attempt is still set aside. A study whose outage condition has its agent read, through the mount, a file only the stopped provider holds will see each such attempt set aside as `cell_unkillable` and run again into the same wait: bounding the read is the study's choice (oneclient's `--provider-timeout`, through `[sandbox.mount] extra_args`, unmeasured and not enabled).
