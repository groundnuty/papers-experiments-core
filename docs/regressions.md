## B. Model backends

**B01. Retry transient API errors with capped exponential backoff.** Retry 429, 408, 409, 5xx, timeouts before a reply, and connection errors. Back off exponentially up to a cap, with jitter, and honour `Retry-After`. Turn SDK-internal retries off so every retry is counted and recorded. *Learned:* PPAM `benchmark/llm_adapters/openai_compat.py:44-84` (dde4246, then 1d41f37 after a 14 s budget proved shorter than a 60 s rate-limit window; 5xx not retried); lost in ICSOC `harness/panel.py:337-348` (one try, then `break`); rebuilt in WWW `harness/agent/providers.py:760-823` (d1e22ac5, 18 Oct) and ICSA `icsa/harness/adapters.py:168-198, 334-358` (4f6d4580, 1 Nov; no jitter, no `Retry-After`). Neither source meets the rule as written: WWW caps `Retry-After` at its maximum delay and then applies jitter of ±25 % (`providers.py:819-823`), so a 60 s header can produce a 45 s sleep. The core applies jitter only above `Retry-After` and never shortens it. *Test:* a fake raising 429 three times then answering yields one turn with three recorded retries and sleeps of at least `Retry-After`; a 400 is not retried.

**B02. Exhausted retries are infrastructure.** A transient error that outlasts the retries ends the attempt as an infrastructure failure, unscored and re-run, never as an agent outcome. *Learned:* WWW `providers.py:896-901`; ICSA `adapters.py:186-195` (`InfraError("endpoint")`). *Test:* N+1 transient errors give `failed:infrastructure` with source `endpoint` and no score.

**B03. A request that was sent and is slow is never resent.** A read timeout after the request went out ends the run at its time cap with usage marked unknown; connect, pool and write timeouts are failures to reach the endpoint and stay infrastructure. A retry that would outlast the run's budget is infrastructure; the run's own deadline is checked before the retry limit. *Learned:* ICSA `adapters.py:83-99, 181-185`, `loop.py:195-197` (final-review fixes, 1 Nov, `docs/harness.md:141-156`); WWW `providers.py:864-907` (1810cfb5, 18 Oct). *Test:* a `ReadTimeout` ends as time cap after exactly one request; a connect timeout is retried and then infrastructure.

**B04. Echo the reasoning field when the model needs it.** Per model and off by default, send the previous turn's reasoning back under the field the deployment expects. Keep it in the transcript either way. *Learned:* PPAM `openai_compat.py:185-193` (HTTP 400 without it; 8f00137, 22bd69f); lost in ICSOC `panel.py:359-372`; rebuilt in WWW `providers.py:227-279` (a2ea65c6, 21 Oct) and ICSA `adapters.py:216-226, 264-265` (1 Nov). *Test:* with echo on, the next request carries the field; with echo off, the wire carries neither it nor the internal copy, and the transcript still holds it.

**B05. Anthropic thinking blocks go back verbatim.** *Learned:* ICSA `adapters.py:384-389`; WWW `providers.py:198-200`. *Test:* the next request's assistant content equals the previous response blocks, signatures included.

**B06. Served-model check.** Record the model id, system fingerprint and every echoed setting of each reply. Treat another id, a changed fingerprint, a setting that differs from the request, or a setting that was never requested (a silent server default) as a mismatch that stops the model's dispatch; treat a reply with no id as unreported. A reply carrying several fingerprints is a change by itself; a dated snapshot id (`<model>-YYYYMMDD`) is the same model. *Learned:* WWW `scripts/run_pilot.py:2175-2283`, `loop.py:488-500, 683-699` (id 57e148c3, 19 Oct; fingerprint c396cc38, 20 Oct; mixed fingerprints c2378e26, 21 Oct); ICSA `icsa/servedsettings.py:22-102`, `campaign/scheduler.py:948-965` (f1c242a8, 3 Nov; "the same silent-default bug", `servedsettings.py:1`). *Test:* `judge` returns mismatch for another id, a changed setting and an unrequested setting; unreported for no id; a missing setting is recorded as "not reported", never as the requested value.

**B07. A listed model is not a servable model.** Admit a model only after a one-token completion succeeds; a `/models` listing is not enough. The completion's reply must report its input and its output tokens: the token budget is held from the counts each reply reports, so a model whose endpoint omits them would be the one model the cap does not bind, which confounds every comparison of models. A probe that returns nothing to read cannot show the counts and is refused the same way. *Learned:* ICSOC `panel.py:776-829` (inactive models and models outside the grant passed the listing); the review of the first real study's budget gate (issue #94) for the usage. *Test:* a fake that lists the id but answers 400 on completion rejects the model before the campaign starts; a completion without one count or both is not admitted, for either SDK, and the model's runs are held as not admitted; a backend whose probe returns nothing is refused, and one that passes its inner probe's reply on is admitted.

**B08. Unfrozen settings refuse a study run.** *Learned:* ICSA `icsa/harness/config.py:210-218` (`assert_frozen`; 9dd6dda5, 1 Nov). This is a configuration gate, separate from B06. *Test:* a model or harness config whose status is not `frozen` raises before any request.

**B09. A rejected key is not retried and not recorded.** 401 and 403 end as `key_rejected` after one request; the SDK's message, which may echo the key, is never recorded. *Learned:* ICSA `adapters.py:32-36, 179-180, 342-343` (f1c242a8, 3 Nov). *Test:* 401 and 403 each give one `key_rejected` after one request, with no SDK text in the record.

**B10. Usage is counted on arrival and never invented.** Count tokens before parsing can fail; a 200 without usage or without choices is infrastructure; unreported usage is `None`, never 0; cached prompt tokens count toward the token budget. *Learned:* ICSA `adapters.py:203-214, 360-371, 390-397` (8bc7ce09, 1 Nov; f1c242a8, 3 Nov); WWW `providers.py:17-28, 301-312`. *Test:* a 200 with usage and no choices raises infrastructure and the usage still counts; input tokens equal uncached plus cache-write plus cache-read.

**B11. Output-token limits fit the model and the endpoint.** `max_tokens` is the study value or the model's own lower maximum, checked against the endpoint's context at admission. *Learned:* ICSA `config.py:88-90` (amendment 6); PPAM `benchmark/panel.py:115-119, 169-173` (402 and context errors); ICSOC reset the limits to 4,096 tokens and 8 rounds (`panel.py:259-260`) after PPAM had raised them for empty answers (cb4a49f). *Test:* a model with a lower maximum sends its own value; a limit over the endpoint's context fails admission.

**B12. A reply cut at the output limit is not an answer.** Record `finish_reason`; a final reply stopped by `length` ends as an output cap, checked before the token budget. *Learned:* PPAM `openai_compat.py:158`; lost in ICSOC `panel.py:355-376`; ICSA `loop.py:151, 220-222`. *Test:* a tool-free reply with stop `length` ends as output cap even when the budget is also exceeded.

**B13. Context overflow is the agent's outcome.** A 400 or 413 that names the context is recorded as context overflow and not retried. *Learned:* WWW `providers.py:691-728` (agent-run/9). *Test:* each tested provider message classifies as overflow.

**B14. Vendor extras pass through.** `extra_body` and provider pinning without fallback reach the request. *Learned:* PPAM `benchmark/panel.py:125-150`, `openai_compat.py:125, 137` (a fallback provider returned gibberish); lost in ICSOC `panel.py:338-345`. *Test:* a condition's extras appear in the request body.

**B15. Record what was sent, not what was meant.** Sampling values in the record come from the request object; credentials are stripped from recorded URLs; keys are read at use time. *Learned:* ICSOC `harness/a2_judge.py:114-117` against `lenses/a2.py:34` (a68ff62); WWW `providers.py:915-923`; ICSA `runner.py:61-70`. *Test:* the recorded temperature equals the request's; a base URL with credentials is recorded without them.

**B16. Incompatible per-model rules are refused before any request.** *Learned:* WWW `loop.py:346-351, 971-998` (echo with reasoning-channel recovery; caps below the notice length). *Test:* each incompatible combination raises at configuration.

**B17. Streamed replies must be complete.** When streaming is used: a reply counts only with the end marker, a finish reason and the final usage chunk; an error event after HTTP 200 is transient; a call without id or name, or a token count that rises with no characters, is rejected and retried; a quiet stream is cut by a whole-request watchdog. *Learned:* WWW `providers.py:1308-1396, 1605-1805` (bec52d27, 1b7b7ec8, 79a3d49c; 19 Oct). Applies when a streaming transport is ported, after v0.1 (see [`architecture.md`](architecture.md#release-boundary)). *Test:* WWW `tests/test_agent_streaming.py` cases.

**B18. A model served by several declared deployments is one model.** A model entry may declare `accepted_fingerprints`, the serving fingerprints of the deployments the study decided are the same model; the set is part of the campaign fingerprint. A reply served under a fingerprint of the set is the model, one under any other sets its run aside as a changed identity (C16), and the served model id is checked as before. The admission probe must be served by the model under a fingerprint of the set. Each declared fingerprint is confirmed by the probe or by the first run whose reply shows it, and one never shown is reported as unconfirmed. Each attempt records the turns each fingerprint served, and the export and the report give each fingerprint's share of the analysed turns and runs. A model that declares no set is checked, recorded and fingerprinted as before. *Learned:* the first study's real-model smoke on a shared inference service (issue #134): a load-balanced endpoint served one model id from two deployments within one run, so the identity check set the run aside, and most long runs would have been. *Test:* a run switching between two declared fingerprints is scored, a third fingerprint sets it aside, a model without the key keeps its fingerprint digest and its checks, the export and the report give the shares, and a resume under another set is refused.

**B19. An abandoned request has a bound on its prompt that is tight where its assumptions hold and the window where they do not.** When the loop gives up a request in flight, or its read timeout fires, nothing comes back, and the only bound was the model's whole context window W for the prompt: about 1.1 M tokens added to a run that had sent 100,000. Both adapters now bound the prompt of every request when they build it, and the record's `route.abandoned_request` carries the bound of the request that was given up: `prompt_bound_tokens` and its basis `prompt_bound_by` (`bytes`, `window` or `none`), the `reply_max_tokens` the request carried, `window_tokens`, and what the conversation tested (`bound_checked`, `bound_exceeded`, `bound_unreported`, `bound_overlapped`). The bound is the last reply's reported prompt and completion, plus the bytes of what was appended since as a chat template writes them (ASCII JSON, with `<`, `>`, `&` and `'` counted as the six bytes `tojson` writes), plus a margin of 32 tokens per appended message and per request; it is W for the first request, after a reply that left a count out, once the bound is W or more, for a history that is no extension of the last reply's (a digest check), and for the rest of a conversation in which a reply reported a prompt above its bound or a request overlapped another. A token is taken to stand for at least one byte, which the tripwire tests and does not prove; the derivation, every term and every assumption are in `expcore.models.request_bound` and [`interfaces.md`](interfaces.md#the-request-given-up). `expcore.campaign.abandoned_bound.abandoned_request_bound` prices it from the record: the reply at the `max_tokens` it carried for an attempt held to it (C27), and the prompt and reply together within W for any other, at the dearest rates of the tiers the prompt bound can reach. The basis it returns carries the tripwire's account for that model in that run (`tripwire_checked`, `tripwire_exceeded`, `tripwire_unreported`, `tripwire_overlapped`, `tripwire_fired_before`; None where the entry lacks the counts), so a study can say what a tight bound rests on. It is recorded only: the budget gate does not read it, and the reservation of C25 and C27 is unchanged. *Learned:* the first study's cost scorer (#189). *Test:* the arithmetic, the bytes (UTF-8, not characters), every fallback to the window, the tripwire and a one-token-per-byte tokenizer as a property; both adapters against a fake client, a resend, a cancel and a timeout; the bound written, loaded and replayed in a record; the dollars for flat, cached and tiered prices, held and not held, and the entries it refuses; the tripwire's account in the basis, clean, fired, absent and per model.

## L. Agent loop and tools

**L01. Malformed tool-call arguments are never run as `{}`.** Do not execute the call; tell the model its arguments were not valid JSON; keep the raw text in history as `{"_raw": "..."}`, because servers reject invalid JSON in history with HTTP 400. Report-and-continue is the default and ending the attempt the declared alternative; executing with `{}` is never offered. Malformed calls are counted per run as a recorded metric. *Learned:* PPAM `openai_compat.py:224-229` and ICSOC `panel.py:380-385` silently ran the tool with `{}`; ICSA fixed it (`adapters.py:102-109, 227-237`, `loop.py:104-107`; `docs/harness.md:25` names the ICSOC base); WWW ends the attempt as `failed:malformed_tool_call` (`loop.py:782-788`; d2d0402b, 19 Oct). Issue #2 listed this item the other way round; the code shows ICSA as the fix. *Test:* arguments `'{"a":'` are not executed, the tool result says so, the resent history is valid JSON holding the raw text, the round counts toward the turn cap, and the run's malformed-call count is 1.

**L02. Unknown tools and wrong argument types are tool errors, not crashes.** *Learned:* ICSA `loop.py:109-111, 148`; WWW `tools.py:693-694, 787`. *Test:* an unknown name returns an error listing the tools.

**L03. Turn cap counts rounds.** A turn with several calls counts once; a tool-free final reply after the last round is allowed. *Learned:* ICSA `loop.py:229-234`. *Test:* three calls in one turn count once; cap + 1 rounds ends as turn cap.

**L04. The agent is charged only for its own time.** Check the wall cap before every model and tool call; exclude waits on infrastructure (store, gate, slot, lock, output validation) from it; the agent's own cap decides before any whole-time ceiling. *Learned:* ICSA `loop.py:185-194`, `runner.py:442-452`; WWW `loop.py:636-651` (ac621236, f7d6a4d6; 20 Oct). *Test:* a slow fake infrastructure call leaves charged time under the cap; own time at the cap gives a wall cap even when the ceiling is also passed.

**L05. No hidden per-call limit.** A tool call is bounded by the run's remaining time, and none starts with less than a second left. *Learned:* ICSA `loop.py:98-101, 112-116` (a hidden 600 s cell cap would have looked like a measured outcome; be25edbc, 1 Nov, amendment 3). *Test:* the timeout passed to the sandbox equals the deadline minus now.

**L06. Tool output is capped by a declared rule, and the rule is pinned.** The cap counts characters, keeps its notice inside the cap, and is stated in the tool description so the tools hash pins it; the full raw result stays in the record. Errors are capped like any output, with the error class first; the full raw error stays in the record, with a truncation flag on what the model saw; the cap value is part of the configuration hash. WWW exempted errors from the cap. *Learned:* ICSA `icsa/harness/capping.py:11-33`, `loop.py:93-96`; WWW `harness/agent/tools.py:13-19, 121-141, 241-303` (9f28d89f, 61474bdc; 19 Oct); PPAM capped only the record and sent the model the full text (`openai_compat.py:34, 238-247`); ICSOC had no cap. *Test:* an output over the cap ends with the notice and stays within it; a long error keeps its class in the capped text, its raw form in the record, and a truncation flag; two caps give two tools hashes and two configuration hashes.

**L07. A truncation by the data source is flagged.** A result exactly at the source's own row or size limit is marked as possibly cut. *Learned:* WWW `tools.py:259-263` (2615bfd0, 20 Oct). *Test:* rows equal to the source limit set the flag.

**L08. A crash in harness code is not the agent's failure.** Record it as a harness defect with a line-free stack hash, set the attempt aside, and re-run it after the fix. *Learned:* WWW `loop.py:277-296, 805-822`; ICSA `runner.py:349-352` and the campaign's same-row re-queue (`store.py:234-249`). *Test:* a tool raising on valid input yields `harness_defect`, never a scored failure.

**L09. Calls after a terminal call are answered "skipped".** History stays byte-identical across a retry branch. *Learned:* WWW `loop.py:611-617, 905-919`. *Test:* calls following a submit are logged skipped.

**L10. Leaked tool calls are detected, not nudged.** A call written as text or in the reasoning channel is labelled. *Learned:* WWW `providers.py:377-511`; PPAM `rescore.py:200-243`. *Test:* each recorded leak shape is labelled; domain JSON naming no tool is not.

**L11. An empty final reply differs from no reply.** *Learned:* PPAM `oracles/placement.py:214-224` (324b72e); ICSOC `panel.py:408-418`. *Test:* the record distinguishes empty content from rounds exhausted.

**L12. MCP failures are split by side.** A closed transport or an internal server error is infrastructure; any other MCP error goes to the model as tool output. *Learned:* ICSA `icsa/harness/knowledge.py:84-95` (ruling of 1 Nov, b449aff1). *Test:* invalid params produce a tool error; a closed connection raises infrastructure.

**L13. The tool manifest is frozen and enforced by the server.** Names, descriptions and schemas must equal the frozen manifest; the allow-list is set server-side; no client-side filter, so a server exposing an extra tool fails to start. An allow-list naming a tool the server lacks also fails at start. *Learned:* ICSA `icsa/knowledge/launch.py:53-80`, `pin.py:82-94`, `harness/knowledge.py:58-60` (bc30a8e5, 1 Nov); PPAM `benchmark/_tool_export.py:22-24`, `test/unit/test_tool_allowlist.py`; ICSOC `panel.py:319-321`. *Test:* an extra tool and a missing tool each fail start.

**L14. A tool server that does not start in time is broken.** *Learned:* ICSA `runner.py:36, 326` (120 s). *Test:* a server that never answers fails start within the bound.

**L15. Blocking waits never run on the event loop.** *Learned:* PPAM `oracles/placement.py:209`, `fixture_runner.py:379` serialised trials (`run_panel.py:26-28`); ICSOC used `asyncio.to_thread` (`runner.py:578-595`). *Test:* two concurrent fake waits overlap in wall time.

**L16. A tool call to an MCP server ends at its `timeout_s`, whether the loop made it or not.** `McpToolProvider.execute` bounds the call by the `timeout_s` it is given, and a server that is up and never answers raises `CallTimedOut`, an `InfraError` of kind `knowledge` that names the tool and the bound. A call made outside the loop (a pre-run check, the day-0 outage check, a health probe) has no other bound, so it hung the attempt, with the lease and the federation held, and recorded nothing. Inside the loop `timeout_s` is the agent's time left, so the call's bound is the loop's own and never longer, and the two expire at one moment: the watch judges the call's expiry as the loop's cut (a time cap, or the ceiling's infrastructure) whichever the event loop runs first, so a hung call at the cap is the agent's outcome and never `knowledge` infrastructure that sets the attempt aside. *Learned:* #204, the first study's review (an `execute` that ignored `timeout_s`, its docstring making the loop's time the call's only limit). *Test:* a server that accepts a call and never answers raises `CallTimedOut` at the bound, naming the tool, and its child is gone; the session serves the next call; a loop run with a hung call ends at its time cap with the call cut; an expiry at the cap or the ceiling is the loop's cut and replays as one, and an expiry with time left is a `knowledge` failure; the outage check records the client's own expiry as `blocked` and timed out, never as `no answer`.

**L17. A tool server's hang past a declared per-call bound is the platform's, not the agent's time, and the bound never reaches a code cell.** With `[agent] tool_server_call_bound_s` declared, a call to a tool server (a provider with a true `tool_server` attribute, `McpToolProvider`) is handed `min(the bound, the agent's time left)` as its `timeout_s`. When the bound is the shorter and the provider runs out of it (`CallTimedOut`), the call is `failed` as `knowledge` infrastructure and the attempt is set aside, never the agent's time cap; when the time left is the shorter, L16's cut decides, a time cap or the ceiling's infrastructure. Every other call, a code cell above all, is handed the time left whatever is declared, what the model is told of a cell that ran long is the text it has without the key, and a call to such a tool that the loop cuts is never judged by the bound. Before the key, a hang inside the loop waited out the whole cap and was scored as the agent's time, so a study whose conditions differ in how many tools they call charged platform hangs to the agent unevenly; and the first form of the bound, `tool_call_bound_s`, was handed to every call, so a study that declared it to classify tool-server hangs also cut every agent code cell at it. Each started call's `elapsed_s` is in the record, so hangs and their cost can be seen per condition, and beside a declared bound `agent_config.tool_server_tools` names the tools it reached. A call to a tool server that the loop cuts at the cap or the ceiling at a reading at or after the bound's deadline had hung first and is judged by the bound too, so the winner does not depend on whether the provider's unwinding or the loop's cut ran first. A study that declares no bound keeps L16's behaviour, and its configuration hash, the record's `agent_config` and the campaign caps are the same bytes: the settings are left out, never a null. *Learned:* #235, a follow-up of #204 (L16), and the review of a study that declared the first form. *Test:* a hung call to a tool server under a declared bound ends as `knowledge` infrastructure having been handed the bound; a bound past the time left hands the time left and ends as a time cap; a call to a tool server cut at the cap after the bound passed, by a provider that honours it or one that ignores it, is `knowledge` infrastructure recorded `cut`, and one cut at the cap before it passed, or at a ceiling nearer than the bound, is the cap's or the ceiling's; the minimum is taken again at every call; a call within the bound is untouched; **a code cell, or any tool that is no tool server's, is handed the time left with the bound declared and is cut at the cap as the agent's time cap even after the bound passed, with the same text and the same record as without the key, through the code tool and the sandbox it runs in; one run with both kinds hands the bound to the tool server's tool alone; the real MCP client under a declared bound ends a hang at the bound;** an undeclared bound hands the time left as before; every started call records its elapsed time and a call that never started has none; the bound, the list of the tools it reached and `elapsed_s` are optional in version 3, refused for an earlier version and when not a finite positive number, a list of names written with the bound and only with it, or a non-negative number; a record written before them replays to its own bytes, a changed `elapsed_s`, bound or list diverges, and a list edited and sealed again diverges at the call; both orders replay, and a code cell cut after the bound replays as the agent's time cap; the sixth merge-point fixture pins the bound, the list and the elapsed times; `[agent] tool_server_call_bound_s` is read as seconds, refused when it is not positive and finite, is in the campaign's caps only when declared, and the old `tool_call_bound_s` is refused at load naming the new key.

## R. Records and replay

**R01. Records are written atomically and read back byte for byte.** Write to a temporary file, fsync, rename; a record written back equals its stored bytes; fields added by a later schema are never written into an older record. *Learned:* WWW `harness/agent/record.py:193-198, 341-351, 378-404` (a60bebc8, 18 Oct); ICSA `campaign/export.py:160-166`. *Test:* load and dump of every fixture record is byte-identical.

**R02. Unknown schema versions and fields are refused.** Validate before writing and at load. *Learned:* WWW `record.py:355-362`; ICSOC `runner.py:690-695` with `schema.py:315-812`. *Test:* an unknown top-level field fails load.

**R03. Replay re-derives every derived field without a model call.** Serve model turns, tool results and clock readings from the record; re-run the real loop; compare transcript, tool-call log, outcome, caps and verdicts; stop at the first divergence. *Learned:* WWW `harness/agent/replay.py` (13 divergence points, 39-454); ICSA had only re-execution of recorded code cells (`icsa/inspection/replayrun.py:402-499`). *Test:* WWW's divergence cases (`tests/test_agent_record_replay.py`) ported to the core format.

**R04. Analysis refuses records without a current replay check.** The check is bound to the code identity and a hash of every input; a check made under other code, with changed inputs, or with an older schema is refused. *Learned:* WWW `harness/agent/replay_check.py:838-918` (3d1a7965, 18 Oct; 2c1d4fc4, 20 Oct). *Test:* each refusal case of `require_current_check`.

**R05. Decisions served during replay are recomputed offline.** *Learned:* WWW `replay_check.py:325-351` (bee4404a, 20 Oct). *Test:* a recorded decision that the offline recompute contradicts holds the batch.

**R06. The echoed request is pinned by a digest.** *Learned:* WWW `replay.py:116-132` (c8b3f32d, 21 Oct). *Test:* tampering with recorded reasoning diverges on replay.

**R07. Records hold no interpreter-specific text.** *Learned:* WWW records hold Python 3.12 error strings and replay only under 3.12 (`tests/test_real_records_roundtrip.py:51-54`). *Test:* exception text is stored as a class name plus a stable message.

**R08. Every archived record set is covered by the roundtrip test, and no output is archived without its replay check.** *Learned:* WWW sharded archives escaped the test glob, and a runner killed by SIGTERM left no replay check (`results/dev-natural-20261020/README.md:34, 42`). *Test:* every `records*.tar.gz` is collected; archiving an output without a check fails.

**R09. An infrastructure failure keeps its partial transcript.** *Learned:* ICSA `runner.py:413-431` (`infra.json` with usage seen so far). *Test:* an endpoint failure at turn 3 leaves turns 1-2 and their usage.

**R10. Unknown is `None`, never 0.** Usage, byte counters, tokens into context and undefined metrics. *Learned:* ICSA `records.py:92`, `sandbox/sandbox.py:1294-1322`, `scoring/cost.py:23-42`; WWW `providers.py:17-28`. *Test:* a missing counter serialises as `null` and is excluded from means.

**R11. **C19. **C23. **C24. A tiered price is applied request by request.** A model's price may be tiers by the request's prompt length, each with a prompt-token boundary and its own input, output and cache prices; a request, its reply included, takes the prices of the tier its prompt fell in. The store keeps each turn's usage, and the cost measure prices each request from it, so a run's cost is what its record's turns give; a tiered attempt without per-turn usage, or with a turn that did not report a count, is charged its bound, never priced at a guessed tier. A model without tiers is priced from its totals as before, and its entry, and so the campaign fingerprint, is unchanged. *Learned:* the first real study on the core (issue #94): a model whose price doubles past a prompt length could only be priced at one tier everywhere. *Test:* tiers load and each prompt finds its tier at the boundary; a table that does not price every prompt once is refused; two requests either side of the boundary cost each its own tier, in the store and from the record read back; a flat price is charged its totals to the bit and keeps its fingerprint; a tiered attempt without per-turn usage is bounded, and one known to hold no turn, a run that found an outage before it started, costs 0; the marker keeps the usage.

**C25. A run's reservation is the most its caps let it cost, the request past its token cap included.** The token cap counts each reply's input and output, summed over the run, and is checked before each request and after each reply, so a run can pass it by one request, whose prompt the context window bounds. A run makes at most one request more than its tool rounds. For a model held to its reply maximum (C27), the requests within the cap are reserved the worst of `input + output <= cap` with output at most the rounds times the reply maximum, at the dearest rates of any tier (input at the dearest of the input and cache prices), never more than the whole cap at the dearest rate, and the request past the cap the window at the input rate and one reply at the output rate. For any other model, the stub and a study's own backend among them, the whole cap and the whole window at the dearest rate; a stub's scripted usage beyond the window is outside the guarantee. With a budget, a run does not start or resume with a planned model that is not free and declares no context window; loading the study for a check, an analysis, a report or a package's check does not need one. *Learned:* the first real study on the core (issue #94): the whole cap at the dearest rate reserved more for one run of a cheap model under a generous cap than the campaign's ceiling, so every run was held; and its review found that a run can end one request past its cap, which no reservation covered, that a stub's reply is not held to the reply maximum, and that requiring the window at every load stopped the analysis of a study made before the rule. *Test:* the worked bound and its parts; output dearer and the replies filling the cap, input dearer; the stub keeps the cap and the window at the dearest rate, and a stub reply longer than its maximum is within the reservation; a run one full request past its cap is within its reservation; random prices, caps and runs that may pass the cap never cost more than their reservation, whose part within the cap is never above the old bound; a model with no window is refused by the gate and the scheduler, not without a budget or when free, and a finished study without windows still checks, analyses, reports and regenerates while `run` refuses it.

**C26. A send the token cap cannot account for reserves its own bound before it is sent.** Two kinds of send escape a run's reservation: a send that failed after it may have been billed (a connection error or a 5xx), which the retrier sends again, and every request after a reply that left its input or its output unreported, since the loop counts the missing count as 0 and the cap then no longer bounds the run. Each is charged a top-up of one request's bound, the bound of the request past the cap, at the dearest prices of any tier: reserved against the campaign's ceilings before the send goes out, under the dispatcher's locks, charged at once and never refunded; the last failed send of a request, after which nothing is sent again, is charged too. A top-up that does not fit is refused, the send is not made, and the attempt ends as infrastructure of kind `budget_hold`: set aside, never treatable, not charged an attempt, and counted per condition and model with the other set-aside attempts, in the export and in a table of the report with a row of zeros for each pair the plan runs. The refusal is the request's recorded failure, so the record replays. Admission's probes are sends too: with a budget, each send of a probe, retries included, is reserved one request's bound by the window before it goes out and charged in the store, an answered one settled to what its reply's counts cost; a probe that does not fit is not sent and its model is not admitted, its reason saying the budget is spent, and a start takes a release before its probes ask for room. The loop's token counting and `token_cap` are unchanged, and without a budget nothing is topped up. *Learned:* the review of the first real study's budget gate (issue #94): a retry of a billed send and the requests after a reply without usage could take a run past its reservation, and so the campaign past its ceiling. *Test:* the retrier tells the guard of each 5xx and connection error, not of a 429 or a 408, and of the last one with no resend; a refused resend is never sent; the recording clears each request and a refusal is its failure; a top-up that fits is spent at once and never refunded, one that does not is refused with the figure; eight top-ups asked for at once take only the room there is; a kill keeps the top-ups on both recovery paths; through the scheduler, a top-up that does not fit is a budget hold set aside, uncharged, among the condition's attempts set aside, in the export and in the report's table by condition and model, and its record replays, while one that fits is charged, and without a budget nothing changes; a campaign whose budget cannot cover a probe sends none and admits no model, at any start; each probe send is charged in the store, kept across a restart and settled to its reply's counts; a probe resent after a 5xx keeps the failed send's bound and reserves the resend, or is a budget hold unsent; a release is taken before the probes ask for room; an attempt held before any reply costs its top-ups alone, and the export counts its usage as complete; a row written before a billed reply that became no turn was checked, from a marker of the time or a store an upgrade brought forward, holds no turn and is still charged its bound; a running attempt whose worker crashed in our own bookkeeping is charged its bound while its siblings run, so a sibling's top-up that only fits without it is refused; a 200 that carries usage and no reply the adapter can read is told to the guard with its counts, for either SDK, and the campaign charges the attempt its bound; a record of a version before the reply-count rule keeps the totals it was written with and replays unchanged, and one of a version under the rule keeps its totals incomplete and round-trips; the report's table counts only budget holds, per condition and model, with a row of zeros for each pair the plan runs; a hold an outage overlapped is counted by its own kind in the export's `budget_holds` and in the report, and an attempt of another kind is not; random runs with retries and replies that leave counts out never cost more than their reservation and top-ups, which some of them do without the top-ups.

**C27. The bound by the reply maximum needs an endpoint shown to hold replies to it.** A run is reserved by the reply maximum R, at most the rounds times R as output and one reply of R past the cap, only for a model whose backend the core's own factory builds (an OpenAI-compatible or Anthropic adapter, which sends R as `max_tokens` in every request) and whose endpoint the admission probe showed applies it: with a budget, at each start, a request with a `max_tokens` of 16 that asks for a long reply must come back cut at that limit, its output count within it. Any other model, one a plugin's factory builds whatever its `backend`, or one the probe did not show, is reserved by its context window and is still admitted, with an event. A reply that later reports more output than R is an event and takes the model off R for the rest of the campaign, a resume included: every run of the model is reserved by the window from then on, those in flight too, and each later request of a run reserved by R goes out only while the campaign is within its ceilings, else it ends as a budget hold. Which bound a run was reserved is the decision of the assessment that admitted it, never the model's status read later, and its attempt's row records it at dispatch: an attempt whose usage is unknown, an interrupted one among them, is charged that bound at every later start, also before admission has shown any model held to R, and never less when a start shows its model held; only a model taken off R charges its attempts by the window whatever their rows say, and a row from before the record follows the gate's view of the model. A resend is cleared again right before it goes out, after the retrier's wait, since the model may have been taken off R during the wait: a top-up reserved by R then reserves the rest of its bound by the window, or the resend is not sent. The reply that broke the rule is outside the guarantee; every request after it is covered. Without a budget no probe of R is sent. *Learned:* the review of the first real study's budget gate (issue #94): R was assumed from the backend's name, so a plugin factory wrapping a core adapter, or an endpoint that ignores `max_tokens`, got the smaller bound; and an interrupted attempt was charged the bound of the model's status at each start, so the start's first gate, which holds no model to R, charged an attempt reserved by R the bound by the window and refused the probes under a ceiling the real total fitted, on every restart. *Test:* the bound by R only when the caller says the model is held to it; only a backend of the core's own factory that sends R is probed, and only with a budget; the probe shows R held only by a reply cut at its small `max_tokens`, not by a longer one, one that stopped by itself or one without its count, for either SDK, and a refused probe is a reason; through the scheduler with the core's factory, a probe that showed it reserves by R, one that did not reserves by the window with an event, a plugin factory's model is reserved by the window and never probed; the store's mark holds across gates and an unreadable mark takes every model off R; a reply past R is an event, the runs in flight are reserved by the window and a later request that no longer fits is a budget hold; a run admitted by R keeps that decision when another attempt takes the model off R before its guard is built, so its first request is checked and held; an attempt reserved by R and killed is charged that bound at the restart, whose probes and runs then fit a ceiling the bound by the window would not, and one reserved by the window stays charged so after a restart that shows its model held; a row recorded by R is charged by the window once its model is taken off R, at any gate, and a row from before the record follows the gate's view; a billed reply past R that the adapter cannot read still takes the model off R; a reply past R of a run reserved by the window takes a model the campaign holds to R off it; a one-token completion answered past its max_tokens of 1 takes the model off R at once, and the probe of R is not sent; a resend whose top-up was reserved by R before the retrier's wait, the model taken off R during it, reserves the rest of its bound by the window, or is a budget hold and is not sent; every resend is cleared again after the wait, whatever failure it follows; random runs against an endpoint that ignores R, or holds to it until one reply goes past it, never cost more than their reservation and top-ups.

**C28. A sharded campaign partitions its plan by pair, the same way on every host.** A campaign run as N shards (`run --shard i/N`) assigns each (task, model, seed) of the whole plan to a shard by ranking each model's pairs by SHA-256 and dealing them round the shards, so every condition of one task, model and seed, and so every pair any contrast forms, lands in one shard, and each shard gets the floor or the ceiling of n/N of each model's pairs; the shards are disjoint and together cover the plan, a sharded plan cannot grow on resume, and the rule is kept with the shard so a store made under another is refused. *Learned:* #154, a main study spread over many hosts. *Test:* the partition over several shard counts, the spec, its labels.

**C29. Shards merge into one batch only when they are one campaign run against one environment.** A merge refuses shards with different fingerprints, rules or counts, overlapping or missing runs, a shard whose own replay check fails, and shards whose recorded environment identities (platform configuration, layout, each space's verified ingest manifest) differ. An identity is names mapped to SHA-256 digests only, since packages are public. *Learned:* #154. *Test:* the identity's form; the merge's refusals; a merged batch's scores and analysis are one driver's byte for byte, and its export and report one driver's apart from what is per driver (each run's dispatch position, start and lease wait, and so a condition's median dispatch position) and what only a merge has, since one driver has no shards to break it down by: the shard tags, `shard_retries_by_kind`, each analysed entry's `wall_s` and `turn_latency_s` (clock readings, checked against the shard's store and the record instead), and the report's `## Shards` section.

**C30. Shares of a campaign's caps and budget never sum past the totals.** Each shard gets an equal part of every `[scheduler.unit_caps]` total and of `max_usd` and `per_model_usd`, the remainder to the first shards; dollars in whole micro-dollars rounded down. A total below the shard count is refused. *Learned:* #154, a model's concurrent sessions and the budget are limits of the whole campaign, not of one host. *Test:* the shares over several totals and counts.

**C31. An instrument that finds its manipulation unrealised sets the attempt aside.** An instrument may read the state at the agent's first turn (`at_first_turn`, before the loop starts the agent's clock, with a reading of the run's clock that the record logs) and may check, once every snapshot is in (`check`), whether the manipulation held. Either refuses with an `InfraError` of a kind no condition can declare as its treatment, and the attempt is set aside and run again like any infrastructure failure. A refusal at the first turn reaches the executor's caller before any request is sent, and the attempt is charged no tokens, unless its backend counted a request. A refusal after the run is recorded (`instrument_refusal`, an optional field of `expcore-record/3`) and applied in the one place a finished attempt is judged after its run, `AttemptRunner._judge`, after the health check and before the identity check, for an attempt the loop scored and for a scored treatment attempt alike, an outage flag on the attempt included (the treatment rule comes before it, so such an attempt is scored until the refusal rewrites it; it is then discarded as the outage's, not charged, and run again); one already set aside keeps its outcome. A kind a condition may declare, or any other exception, is a defect of the instrument. A study whose instruments have neither method takes no reading and writes no field: its records are unchanged. Instruments nest: they start in list order and finish in the reverse of it, so an instrument listed earlier finishes later, and a probe listed after a fault injector or a progressive ingest reads the state before the restore. The record keeps its instruments in list order, a `finish` that raises does not stop the others, and the first-turn hooks and the checks stay in list order, so the first listed instrument that refuses is the refusal the record keeps. *Learned:* #135, found by the first study's second design, whose manipulation was defined at the agent's first turn, and whose attempts were scored whether or not it held, so a study could only mark their outcomes as not determined. *Test:* the hook's reading, order and refusals; a check's refusal in the record and nothing in a record without one; a malformed or treatable refusal refused at load; the scheduler sets a scored attempt, and a scored treatment attempt, one the health gate reported an outage for too included, aside and runs it again, and leaves a set-aside outcome as it was; the example study's records have neither the reading nor the field; the fourth merge-point fixture replays byte for byte; the finishes are the reverse of the starts, an instrument listed after another starts after it and finishes before it, the hooks and the checks keep list order and the first listed refusal is the one recorded, a finish that raises stops no other, the record's `instruments` are keyed in list order, and a probe listed after the real fault injector reads before the provider is restored while one listed before it reads after.

**C32. A shard never holds pairs it cannot run, and a campaign can shard by model.** A shard that holds pairs of a model whose concurrency share is 0 is refused at start, naming the model, under either rule. `[shards] per_model` in `campaign.toml` (rule `expcore-shard/3`, in the campaign fingerprint) maps shard i to one model in declared order, deals that model's pairs among its own shards as C28 deals them, and gives each shard a cap of one run, so a model's shard count is its concurrent sessions; a model's `per_model_usd` is split over its shards, and `max_usd` over the priced models' shards in proportion to planned runs times one run's reservation, in micro-dollars rounded down, free models' shards getting 0. Refused: counts above a unit's cap, an N that is not their sum, a model of the plan without a count, and a budget that cannot pay one run's reservation for every priced shard. Stores made under `expcore-shard/2` still resume and merge. *Learned:* #154, one federation per concurrent run makes 60 to 140 shards against a model's 20 concurrent sessions, and the balanced deal handed pairs to shards with none of the model's sessions. *Test:* the mapping and the per-model balance, the refusals, the budget split, a campaign split by model and merged equal to one driver as C29 says, also when only some of its models declare accepted fingerprints (B18), so the shards' exports differ in `deployment_shares`.

**C33. A start the platform holds back costs no attempt, and the campaign holds instead of spinning.** A platform registers a hold kind with `register_infra_kind(..., treatable=False, charged=False)`: an attempt that ends in it is set aside uncharged under the same attempt number, as a `budget_hold` is, however often, so no run is lost to `max_attempts` for it; a hold must be untreatable, and a kind cannot be made charged or free by registering it again. **S13. A ratio outcome sums every run, a zero sum is declared, never a number, and its cells are never independent units.** A contrast of an outcome per unit of another (`estimator = "ratio"`, a `numerator` and a `denominator`, such as tokens per correct result) compares a ratio of sums, not a mean of per-run ratios: in each cell each arm's numerator and denominator are summed over its used pairs, every task and seed together, and a run whose denominator is 0 still adds its numerator. **S15. Equivalence claims made together are decided together, and only when reachable.** A preregistration may declare `equivalence_family`: members of the Holm family, each with an `equivalence_margin` and an estimator that registers a TOST p-value; it is refused beside `exploratory_only`, and a member outside the Holm family, without a margin or without that hook is refused naming it.
